## Kontext der Aufgabe

In Aufgabe 13(b) soll IPsec deaktiviert und die vorherige VPN-Aufgabe mit OpenVPN wiederholt werden.  
Der Tunnel soll zwischen den beiden Rechnern `gwsec` und `pcsec1` aufgebaut werden.

Die geforderten VPN-Adressen sind:

| Rechner | normale Labor-IP | VPN-IP im OpenVPN-Tunnel |
|---|---:|---:|
| `gwsec` | `10.153.210.1` | `10.1.0.1` |
| `pcsec1` | `10.153.210.2` | `10.1.0.2` |

Zusätzlich verlangt die Aufgabe, dass die OpenVPN-Konfiguration mit folgendem Befehl startbar ist:

```bash
systemctl start openvpn@secp
```

Das bedeutet: Die OpenVPN-Konfiguration muss unter diesem Pfad liegen:

```bash
/etc/openvpn/secp.conf
```

Denn `openvpn@secp` sucht automatisch nach der Datei `secp.conf` im OpenVPN-Konfigurationsverzeichnis.

# Teil 13(b), OpenVPN

## 1. Ziel der Umsetzung

Wir bauen einen einfachen OpenVPN Point-to-Point Tunnel zwischen `gwsec` und `pcsec1`.

Das Zielbild ist:

```text
pcsec1                         gwsec
10.153.210.2  <------------->  10.153.210.1
10.1.0.2       OpenVPN-Tunnel  10.1.0.1
```

Die IPs `10.153.210.1` und `10.153.210.2` sind die normalen Netzwerkadressen der Maschinen im Labor.  
Darüber läuft die eigentliche UDP-Verbindung von OpenVPN.

Die IPs `10.1.0.1` und `10.1.0.2` sind die virtuellen Tunneladressen.  
Über diese IPs testen wir später, ob der VPN-Tunnel funktioniert.

---

## 2. Warum IPsec zuerst deaktiviert werden musste

Die Aufgabe sagt ausdrücklich, dass IPsec deaktiviert werden soll, bevor OpenVPN eingerichtet wird.

Dafür haben wir auf beiden Rechnern IPsec beendet und die XFRM States und Policies geleert.

Auf `gwsec` und `pcsec1`:

```bash
swanctl --terminate --ike secp 2>/dev/null || true
ip xfrm state flush
ip xfrm policy flush
systemctl stop strongswan 2>/dev/null || true
```

### Erklärung der Befehle

```bash
swanctl --terminate --ike secp
```

Beendet die aktive IKE-Verbindung mit dem Namen `secp`, falls sie noch läuft.

```bash
2>/dev/null || true
```

Unterdrückt Fehlermeldungen, falls keine Verbindung existiert.  
Das ist praktisch, damit das Skript nicht unnötig abbricht.

```bash
ip xfrm state flush
```

Löscht die aktiven IPsec Security Associations aus dem Kernel.

```bash
ip xfrm policy flush
```

Löscht die IPsec Policies aus dem Kernel.

```bash
systemctl stop strongswan
```

Stoppt den strongSwan Dienst.

### Warum ist das wichtig?

Wenn IPsec noch aktiv ist, kann der Traffic zwischen `pcsec1` und `gwsec` weiterhin durch IPsec verändert oder verschlüsselt werden.  
Dann wäre nicht mehr eindeutig, ob der spätere Ping wegen OpenVPN funktioniert oder noch wegen IPsec.  
Außerdem könnten IPsec Policies Pakete beeinflussen, die eigentlich über OpenVPN laufen sollen.

## 3. Firewall vorübergehend deaktivieren

Da VPN-Protokolle oft durch Firewall-Regeln blockiert werden, haben wir die Firewall-Regeln vorübergehend entfernt.

Auf beiden Rechnern:

```bash
systemctl stop nftables 2>/dev/null || true
systemctl stop ufw 2>/dev/null || true

iptables -P INPUT ACCEPT
iptables -P OUTPUT ACCEPT
iptables -P FORWARD ACCEPT

iptables -F
iptables -t nat -F
iptables -t mangle -F
```

### Erklärung

```bash
systemctl stop nftables
```

Stoppt `nftables`, falls es aktiv ist.

```bash
systemctl stop ufw
```

Stoppt `ufw`, falls es aktiv ist.

```bash
iptables -P INPUT ACCEPT
iptables -P OUTPUT ACCEPT
iptables -P FORWARD ACCEPT
```

Setzt die Standardregeln für eingehende, ausgehende und weitergeleitete Pakete auf `ACCEPT`.

```bash
iptables -F
```

Löscht die normalen Filter-Regeln.

```bash
iptables -t nat -F
```

Löscht NAT-Regeln.

```bash
iptables -t mangle -F
```

Löscht Mangle-Regeln, also Regeln, die Pakete verändern können.

### Warum ist das wichtig?

OpenVPN nutzt in dieser Konfiguration UDP-Port `1194`.  
Wenn eine Firewall diesen Port blockiert, kann der Tunnel nicht aufgebaut werden.  
Für die Praktikumsaufgabe ist es deshalb einfacher, die Firewall vorübergehend zu deaktivieren.

## 5. OpenVPN Static Key erzeugen

Auf `gwsec` wurde ein gemeinsamer statischer Schlüssel erzeugt.

```bash
mkdir -p /home/secpgast/Abgaben/13
mkdir -p /etc/openvpn

openvpn --genkey --secret /home/secpgast/Abgaben/13/secp.key

cp /home/secpgast/Abgaben/13/secp.key /etc/openvpn/secp.key
chmod 600 /home/secpgast/Abgaben/13/secp.key /etc/openvpn/secp.key
```

### Erklärung

```bash
mkdir -p /home/secpgast/Abgaben/13
```

Erstellt den Abgabeordner für Aufgabe 13, falls er noch nicht existiert.

```bash
mkdir -p /etc/openvpn
```

Erstellt das OpenVPN-Konfigurationsverzeichnis, falls es noch nicht existiert.

```bash
openvpn --genkey --secret /home/secpgast/Abgaben/13/secp.key
```

Erzeugt einen statischen OpenVPN-Schlüssel.  
Dieser Schlüssel ist das gemeinsame Geheimnis zwischen `gwsec` und `pcsec1`.

```bash
cp /home/secpgast/Abgaben/13/secp.key /etc/openvpn/secp.key
```

Kopiert den Schlüssel in das Verzeichnis, aus dem OpenVPN ihn später liest.

```bash
chmod 600 ...
```

Setzt die Berechtigungen so, dass nur `root` die Datei lesen und schreiben kann.

### Warum brauchen beide Rechner denselben Key?

Wir verwenden OpenVPN im Static-Key-Modus.  
Dabei gibt es keine Zertifikate und keine PKI.  
Stattdessen haben beide Endpunkte exakt denselben geheimen Schlüssel.

Wenn die Schlüssel unterschiedlich sind, kann OpenVPN die Pakete nicht entschlüsseln und der Tunnel funktioniert nicht.

## 6. Wichtiger Hinweis zum Secret

Der Inhalt der Datei `secp.key` ist ein Secret.  
Er sollte nicht in einer öffentlichen Dokumentation oder in Screenshots veröffentlicht werden.

Der Key hat grundsätzlich diese Struktur:

```text
#
# 2048 bit OpenVPN static key
#
-----BEGIN OpenVPN Static key V1-----
...
-----END OpenVPN Static key V1-----
```

Wichtig ist:  
Die Datei muss vollständig kopiert werden, inklusive Header und Footer.

Nicht ausreichend ist es, nur die Hex-Zeilen zwischen `BEGIN` und `END` zu kopieren.

## 7. Key von gwsec auf pcsec1 kopieren

Nachdem der Key auf `gwsec` erzeugt wurde, wurde er auf `pcsec1` kopiert.

Auf `gwsec`:

```bash
scp /home/secpgast/Abgaben/13/secp.key root@10.153.210.2:/home/secpgast/Abgaben/13/secp.key
```

Ergebnis:

```text
secp.key 100% 636 262.8KB/s 00:00
```

Danach auf `pcsec1`:

```bash
mkdir -p /etc/openvpn
cp /home/secpgast/Abgaben/13/secp.key /etc/openvpn/secp.key
chmod 600 /home/secpgast/Abgaben/13/secp.key /etc/openvpn/secp.key
```

### Warum haben wir `scp` verwendet?

`scp` kopiert die Datei vollständig und unverändert.  
Das ist bei einem Schlüssel wichtig, weil schon kleine Änderungen oder fehlende Zeilen dazu führen, dass OpenVPN den Key nicht akzeptiert.

## 8. Fehler, der auf pcsec1 passiert ist

Auf `pcsec1` wurde der Key zuerst manuell eingefügt. Dabei wurden nur die Hex-Zeilen eingefügt, aber Header und Footer fehlten.

Dadurch kam beim Start von OpenVPN folgender Fehler:

```text
Insufficient key material or header text not found in file '/etc/openvpn/secp.key' (0/128/256 bytes found/min/max)
Exiting due to fatal error
```

### Bedeutung des Fehlers

OpenVPN konnte die Datei `/etc/openvpn/secp.key` nicht als gültigen Static Key erkennen.

Grund:

Die Datei enthielt nicht die vollständige OpenVPN-Key-Struktur.

Es fehlte insbesondere:

```text
-----BEGIN OpenVPN Static key V1-----
```

und:

```text
-----END OpenVPN Static key V1-----
```

### Lösung

Die kaputte Key-Datei auf `pcsec1` löschen und den Key erneut vollständig von `gwsec` kopieren.

Auf `pcsec1`:

```bash
systemctl stop openvpn@secp 2>/dev/null || true

rm -f /home/secpgast/Abgaben/13/secp.key
rm -f /etc/openvpn/secp.key

mkdir -p /home/secpgast/Abgaben/13
mkdir -p /etc/openvpn
```

Auf `gwsec`:

```bash
scp /home/secpgast/Abgaben/13/secp.key root@10.153.210.2:/home/secpgast/Abgaben/13/secp.key
```

Auf `pcsec1`:

```bash
cp /home/secpgast/Abgaben/13/secp.key /etc/openvpn/secp.key
chmod 600 /home/secpgast/Abgaben/13/secp.key /etc/openvpn/secp.key
```

# 10. OpenVPN-Konfiguration auf gwsec

Auf `gwsec` wurde folgende Konfiguration erstellt:

```bash
cat > /home/secpgast/Abgaben/13/secp.conf <<'EOF'
dev tun
proto udp
port 1194

ifconfig 10.1.0.1 10.1.0.2

secret /etc/openvpn/secp.key

cipher AES-256-CBC
auth SHA256

persist-key
persist-tun

verb 3
EOF

ln -sf /home/secpgast/Abgaben/13/secp.conf /etc/openvpn/secp.conf
```

## Erklärung der Konfiguration auf gwsec

```conf
dev tun
```

OpenVPN erstellt ein TUN-Interface.  
Ein TUN-Interface arbeitet auf Layer 3, also mit IP-Paketen.

```conf
proto udp
```

OpenVPN verwendet UDP.  
UDP ist für VPNs üblich, weil es weniger Overhead als TCP hat.

```conf
port 1194
```

OpenVPN lauscht auf Port `1194`.  
Das ist der Standardport für OpenVPN.

```conf
ifconfig 10.1.0.1 10.1.0.2
```

Setzt die Tunneladresse von `gwsec` auf `10.1.0.1` und den Peer auf `10.1.0.2`.

```conf
secret /etc/openvpn/secp.key
```

Sagt OpenVPN, dass der statische Schlüssel unter `/etc/openvpn/secp.key` liegt.

```conf
cipher AES-256-CBC
```

Verwendet AES-256-CBC als Verschlüsselungsalgorithmus.

```conf
auth SHA256
```

Verwendet SHA-256 für die HMAC-Authentifizierung der Pakete.

```conf
persist-key
```

Verhindert, dass der Key bei bestimmten Neustarts neu gelesen werden muss.

```conf
persist-tun
```

Verhindert, dass das TUN-Interface bei bestimmten Neustarts neu erstellt werden muss.

```conf
verb 3
```

Setzt die Log-Ausgabe auf ein normales, hilfreiches Level.

```bash
ln -sf /home/secpgast/Abgaben/13/secp.conf /etc/openvpn/secp.conf
```

Erstellt einen symbolischen Link von der Abgabedatei zur Datei, die OpenVPN beim Start mit `openvpn@secp` erwartet.

## Erklärung der Konfiguration auf pcsec1

```conf

```

Erstellt ein TUN-Interface für IP-Pakete.

```conf

```

Verwendet UDP für den Transport.

```conf

```

Sagt `pcsec1`, dass es sich zu `gwsec` unter der Labor-IP `10.153.210.1` auf UDP-Port `1194` verbinden soll.

```conf

```

Der Client bindet sich nicht fest an einen lokalen Port.  
Er verwendet einen dynamisch gewählten lokalen UDP-Port.

```conf

```

Setzt die Tunneladresse von `pcsec1` auf `10.1.0.2` und den Peer auf `10.1.0.1`.

```conf

```

Verwendet denselben Static Key wie `gwsec`.

```conf

```

Muss auf beiden Seiten identisch sein.  
Sonst können die Pakete nicht korrekt verschlüsselt und authentifiziert werden.

```conf
persist-key
persist-tun
verb 3
```

Gleiche Bedeutung wie auf `gwsec`.

# 12. Warum die Konfiguration über `openvpn@secp` startbar ist

Die Aufgabe verlangt:

```bash
systemctl start openvpn@secp
```

Der Name nach dem `@` ist `secp`.

Deshalb sucht systemd nach:

```bash
/etc/openvpn/secp.conf
```

Wir haben deshalb auf beiden Rechnern einen Symlink erstellt:

```bash
ln -sf /home/secpgast/Abgaben/13/secp.conf /etc/openvpn/secp.conf
```

Dadurch liegt die eigentliche Datei im Abgabeordner, aber OpenVPN kann sie trotzdem über den erwarteten Pfad finden.

Das erfüllt gleichzeitig:

1. Die Konfigurationsdatei liegt im Abgabeordner.
2. Die Konfiguration ist über `systemctl start openvpn@secp` startbar.

# Teil 13(c), Theorie: Vergleich IPsec und OpenVPN in der Praxis

## 1. Grundidee von IPsec

IPsec ist eine VPN-Technologie auf Netzwerkebene.  
Sie arbeitet direkt auf Layer 3 des OSI-Modells, also auf IP-Ebene.

Das bedeutet: IPsec schützt IP-Pakete selbst.  
Anwendungen müssen dafür nichts wissen oder anpassen.

In Linux wird IPsec über XFRM Policies und XFRM States im Kernel umgesetzt.

Beispiele:

```bash
ip xfrm policy
ip xfrm state
```

`ip xfrm policy` zeigt, welcher Verkehr geschützt werden soll.  
`ip xfrm state` zeigt die konkreten Security Associations, also wie der Verkehr geschützt wird.

---

## 2. Vorteile von IPsec

### Vorteil 1: Sehr transparent für Anwendungen

IPsec läuft auf IP-Ebene.  
Anwendungen merken meistens nicht, dass der Verkehr verschlüsselt wird.

Beispiel:

Ein Ping von `pcsec1` zu `gwsec` sieht für die Anwendung wie normaler IP-Verkehr aus.  
Der Kernel entscheidet anhand der Policies, ob das Paket verschlüsselt werden muss.

### Vorteil 2: Gut für Site-to-Site VPNs

IPsec ist sehr verbreitet für Standortkopplungen, also zum Beispiel:

```text
Firmennetz A <---- IPsec ----> Firmennetz B
```

Viele Router, Firewalls und Gateways unterstützen IPsec direkt.

### Vorteil 3: Kernel-Integration

Da IPsec tief im Betriebssystem integriert ist, kann es sehr effizient sein.

### Vorteil 4: Standardisiert

IPsec ist ein etablierter Standard und wird von vielen Herstellern unterstützt.

---

## 3. Nachteile von IPsec

### Nachteil 1: Komplexe Konfiguration

IPsec ist oft schwerer zu konfigurieren als OpenVPN.  
Man muss IKE, Proposals, Policies, Traffic Selectors, Authentifizierung und Security Associations verstehen.

In Aufgabe 13(a) hatten wir zum Beispiel Probleme mit:

```text
NO_PROPOSAL_CHOSEN
```

und:

```text
no IKE config found
```

Das zeigt, dass kleine Unterschiede in der Konfiguration dazu führen können, dass der Tunnel nicht aufgebaut wird.

### Nachteil 2: Debugging ist schwieriger

Fehler können an vielen Stellen entstehen:

- IKE Proposal passt nicht
- ESP Proposal passt nicht
- PSK passt nicht
- Traffic Selectors passen nicht
- Policies sind nicht geladen
- States sind veraltet
- Firewall blockiert UDP 500, UDP 4500 oder ESP

### Nachteil 3: NAT kann Probleme machen

IPsec nutzt ESP und IKE.  
NAT kann dabei Probleme verursachen, weshalb NAT Traversal über UDP 4500 notwendig ist.

### Nachteil 4: Weniger flexibel im User-Space

IPsec arbeitet stark kernelbasiert.  
Das ist effizient, aber manchmal weniger flexibel als ein User-Space VPN wie OpenVPN.

---

## 4. Grundidee von OpenVPN

OpenVPN ist ein VPN-System, das im User-Space läuft.  
Es erstellt ein virtuelles Netzwerkinterface, zum Beispiel `tun0`.

Daten werden dann über dieses Interface geschickt und von OpenVPN verschlüsselt über UDP oder TCP transportiert.

In unserer Aufgabe wurde UDP-Port `1194` verwendet.

---

## 5. Vorteile von OpenVPN

### Vorteil 1: Einfacher zu verstehen

OpenVPN-Konfigurationen sind oft leichter lesbar.

Beispiel:

```conf
remote 10.153.210.1 1194
ifconfig 10.1.0.2 10.1.0.1
secret /etc/openvpn/secp.key
```

Man sieht direkt:

- wohin verbunden wird
- welche VPN-IP verwendet wird
- welcher Schlüssel genutzt wird

### Vorteil 2: Läuft über einen normalen UDP- oder TCP-Port

OpenVPN nutzt normale Ports, meist UDP `1194`.  
Das ist oft einfacher durch Firewalls zu erlauben als ESP bei IPsec.

### Vorteil 3: Einfaches Debugging

Man kann den Dienst direkt prüfen:

```bash
systemctl status openvpn@secp
journalctl -u openvpn@secp
ip addr show tun0
tcpdump -ni ens7 udp port 1194
```

### Vorteil 4: Flexibel

OpenVPN kann viele Szenarien abbilden:

- Point-to-Point
- Remote Access VPN
- Site-to-Site VPN
- TUN-Modus
- TAP-Modus
- UDP
- TCP
- Static Key
- Zertifikate

### Vorteil 5: Gut für Remote Access

OpenVPN wird häufig genutzt, um einzelne Clients sicher in ein Netzwerk zu bringen.

---

## 6. Nachteile von OpenVPN

### Nachteil 1: Läuft im User-Space

OpenVPN läuft nicht direkt im Kernel wie IPsec.  
Dadurch kann es bei hoher Last weniger performant sein.

### Nachteil 2: Zusätzlicher Prozess

Der OpenVPN-Prozess muss laufen.  
Wenn der Dienst abstürzt oder nicht gestartet ist, ist der Tunnel weg.

### Nachteil 3: Static-Key-Modus ist nicht ideal für große Setups

In unserer Aufgabe nutzen wir einen Static Key.  
Das ist einfach für zwei Rechner, aber schlecht skalierbar.

Bei vielen Clients müsste man Schlüssel sauber verteilen und verwalten.  
In echten Umgebungen nutzt man daher meistens Zertifikate und eine PKI.

### Nachteil 4: Nicht so transparent wie IPsec

OpenVPN erzeugt ein eigenes Interface, zum Beispiel `tun0`.  
Routing und Interfaces müssen richtig eingerichtet sein.

---

# 7. Direkter Vergleich

| Kriterium | IPsec | OpenVPN |
|---|---|---|
| Ebene | Layer 3, direkt auf IP-Ebene | User-Space mit virtuellem TUN/TAP Interface |
| Typische Nutzung | Site-to-Site VPN, Gateway-to-Gateway | Remote Access, flexible VPNs, auch Site-to-Site |
| Konfiguration | komplexer | meist einfacher |
| Debugging | schwieriger, viele Kernel/XFRM/IKE-Komponenten | einfacher über Logs, systemctl, tun0 |
| Firewall/NAT | ESP, UDP 500, UDP 4500, NAT-T | meist UDP 1194 oder TCP |
| Performance | oft sehr gut wegen Kernel-Integration | abhängig vom User-Space Prozess |
| Standardisierung | stark standardisiert, herstellerübergreifend | sehr verbreitet, aber eigene OpenVPN-Lösung |
| Skalierung | gut mit professionellen Gateways | gut mit Zertifikaten, Static Key aber schlecht skalierbar |
| Transparenz | sehr transparent für Anwendungen | nutzt eigenes Tunnelinterface |
| Praxisvorteil | gut für feste Netzwerkverbindungen | gut für flexible Client-VPNs |

---

# 8. Welche Lösung ist in der Praxis besser?

Es gibt nicht die eine bessere Lösung.  
Es hängt vom Einsatzfall ab.

## IPsec ist oft besser, wenn:

- zwei Standorte dauerhaft verbunden werden sollen
- Firewalls oder Router IPsec nativ unterstützen
- hohe Performance wichtig ist
- der VPN-Verkehr transparent für Anwendungen sein soll
- man eine klassische Site-to-Site-Kopplung baut

## OpenVPN ist oft besser, wenn:

- einzelne Clients Zugriff auf ein Netzwerk brauchen
- eine einfachere Konfiguration gewünscht ist
- man über normale UDP- oder TCP-Ports gehen möchte
- Debugging und Betrieb möglichst unkompliziert sein sollen
- man eine flexible User-Space Lösung bevorzugt

# 10. Mögliche Theorieantwort für Aufgabe 13(c)

```text
IPsec arbeitet direkt auf IP-Ebene und ist daher für Anwendungen sehr transparent. 
Es eignet sich besonders gut für Site-to-Site-VPNs und wird von vielen Routern, Firewalls und Gateways unterstützt. 
Ein Vorteil ist die tiefe Integration in den Kernel und die weite Standardisierung. 
Nachteilig ist jedoch die vergleichsweise komplexe Konfiguration mit IKE, Proposals, Security Associations, Traffic Selectors und XFRM Policies. 
Auch das Debugging kann schwieriger sein, insbesondere bei NAT, Firewalls oder nicht passenden Crypto-Proposals.

OpenVPN läuft dagegen im User-Space und erzeugt ein eigenes virtuelles Netzwerkinterface, zum Beispiel tun0. 
Es ist häufig einfacher einzurichten und zu debuggen, da man den Dienst mit systemctl, journalctl, ip addr und tcpdump gut prüfen kann. 
Außerdem nutzt OpenVPN normale UDP- oder TCP-Ports, was in manchen Netzen einfacher durch Firewalls geht. 
Ein Nachteil ist, dass OpenVPN als User-Space-Prozess bei hoher Last weniger performant sein kann als kernelnahes IPsec. 
Der Static-Key-Modus ist außerdem nur für kleine Point-to-Point-Szenarien geeignet und skaliert schlecht.

In der Praxis wird IPsec häufig für feste Standortkopplungen verwendet, während OpenVPN oft für flexible Client- oder Remote-Access-VPNs genutzt wird.
```

# 11. Zusammenfassung

Für Aufgabe 13(b) wurde IPsec deaktiviert und OpenVPN als Point-to-Point-VPN eingerichtet.

Wichtige Ergebnisse:

- `gwsec` nutzt im Tunnel die IP `10.1.0.1`
- `pcsec1` nutzt im Tunnel die IP `10.1.0.2`
- die OpenVPN-Konfiguration liegt als `secp.conf` im Abgabeordner
- über einen Symlink liegt sie zusätzlich unter `/etc/openvpn/secp.conf`
- der Start erfolgt über `systemctl start openvpn@secp`
- der gemeinsame Static Key liegt unter `/etc/openvpn/secp.key`
- der Key muss auf beiden Rechnern identisch sein
- ein häufiger Fehler war eine unvollständige Key-Datei auf `pcsec1`
- die Lösung war das vollständige Kopieren des Keys per `scp`

Wichtige finale Befehle:

```bash
# gwsec zuerst
systemctl start openvpn@secp
systemctl status openvpn@secp --no-pager

# danach pcsec1
systemctl start openvpn@secp
systemctl status openvpn@secp --no-pager

# prüfen
ip addr show tun0
ping -c 3 10.1.0.1
```
