# Praktikum IT-Sicherheit, Blatt 05, Aufgabe 13(a): IPsec mit strongSwan und swanctl

## 1. Ziel der Aufgabe

In Aufgabe 13(a) sollte ein IPsec Setup zwischen den beiden Rechnern `pcsec1` und `gwsec` eingerichtet werden.

Die Verbindung wurde mit `strongSwan` umgesetzt. Die Verwaltung der Verbindung erfolgte mit `swanctl`. Für die Authentifizierung wurde ein Pre-Shared Key verwendet.

Die zentrale Idee ist:

```text
pcsec1  <==== IPsec verschlüsselt ====>  gwsec
10.153.210.2                            10.153.210.1
```

Der normale Netzwerkverkehr zwischen `pcsec1` und `gwsec`, zum Beispiel ein Ping, soll nicht einfach ungeschützt über das Netzwerk laufen. Stattdessen soll der Linux Kernel diesen Verkehr anhand von IPsec Policies erkennen und mit ESP schützen.

ESP steht für Encapsulating Security Payload. ESP schützt die Pakete durch Verschlüsselung und Authentifizierung. Dadurch kann ein Angreifer auf dem Netzwerk den Inhalt der Pakete nicht einfach lesen oder unbemerkt verändern.

## 2. Beteiligte Rechner

Für diese Aufgabe wurden genau zwei Rechner verwendet:

| Rechner | Rolle | IPv4-Adresse |
|---|---|---|
| `gwsec` | Gateway, IPsec Gegenstelle | `10.153.210.1` |
| `pcsec1` | Client, IPsec Gegenstelle | `10.153.210.2` |

`pcsec2` wurde für Aufgabe 13(a) nicht benötigt, weil die Aufgabe den Verkehr zwischen `pcsec1` und `gwsec` verlangt.

Auf `gwsec` wurde mit `ip -4 -br addr` geprüft, welche IPv4-Adressen vorhanden sind:

```text
lo               UNKNOWN        127.0.0.1/8
ens7             UP             10.153.210.1/29
ens8             UP             10.153.210.193/26
```

Für den IPsec Tunnel wurde die Schnittstelle `ens7` verwendet, da `gwsec` dort die Adresse `10.153.210.1/29` hat. Die passende Gegenseite in diesem kleinen Netz ist `pcsec1` mit `10.153.210.2`.

### Warum wurde strongSwan installiert?

`strongSwan` ist die Software, die den IKE Daemon bereitstellt. Der Daemon heißt `charon`. Er verhandelt die IPsec Security Associations mit der Gegenseite.

`strongswan-swanctl` liefert das Tool `swanctl`. Damit können Konfigurationen geladen, Tunnel gestartet und aktive Security Associations angezeigt werden.

Wichtig ist dabei:

```text
strongSwan/charon verhandelt IPsec.
swanctl steuert und lädt die Konfiguration.
der Linux Kernel setzt die IPsec Policies und States technisch um.
```

## 4. Firewall vorübergehend deaktivieren

Die Aufgabe verlangt, dass die Firewall für die folgenden Aufgaben vorübergehend deaktiviert wird. Deshalb wurden auf beiden Rechnern die Firewall Dienste gestoppt und die iptables Regeln geleert.

```bash
systemctl stop nftables 2>/dev/null || true
systemctl stop ufw 2>/dev/null || true

iptables -P INPUT ACCEPT
iptables -P OUTPUT ACCEPT
iptables -P FORWARD ACCEPT

iptables -F
iptables -t nat -F
iptables -t mangle -F
```

### Erklärung der Befehle

```bash
systemctl stop nftables 2>/dev/null || true
```

Dieser Befehl versucht, `nftables` zu stoppen. Falls der Dienst nicht existiert oder nicht läuft, wird der Fehler nach `/dev/null` umgeleitet. Das `|| true` sorgt dafür, dass das Skript trotzdem weiterläuft.

```bash
systemctl stop ufw 2>/dev/null || true
```

Dieser Befehl macht dasselbe für `ufw`. Auf vielen Debian Systemen ist `ufw` nicht aktiv, daher ist es normal, wenn hier kein sichtbarer Output kommt.

```bash
iptables -P INPUT ACCEPT
iptables -P OUTPUT ACCEPT
iptables -P FORWARD ACCEPT
```

Diese Befehle setzen die Standard-Policies auf `ACCEPT`. Dadurch wird eingehender, ausgehender und weitergeleiteter Verkehr standardmäßig erlaubt.

```bash
iptables -F
iptables -t nat -F
iptables -t mangle -F
```

Diese Befehle löschen bestehende Regeln in den Tabellen `filter`, `nat` und `mangle`.

### Warum war das wichtig?

IPsec verwendet unter anderem UDP Port 500 für IKE und UDP Port 4500 für NAT Traversal. Zusätzlich wird ESP verwendet. Wenn eine Firewall diesen Verkehr blockiert, kann der Tunnel nicht aufgebaut werden oder der Ping funktioniert nicht über IPsec.

## 7. Verwendeter Pre-Shared Key

Für IKE wurde dieser Pre-Shared Key verwendet:

```text
12345678
```

Dieser Wert muss auf beiden Seiten identisch sein.

### Was ist ein Pre-Shared Key?

Ein Pre-Shared Key, kurz PSK, ist ein gemeinsames Geheimnis, das beide IPsec Endpunkte vorher kennen müssen. Beim Aufbau der IKE Verbindung beweisen beide Seiten, dass sie denselben Secret kennen.

In dieser Aufgabe ist das ausreichend, weil explizit das Pre-Shared-Key-Verfahren verlangt wurde.

### Sicherheitshinweis

In einer echten Produktivumgebung wäre `12345678` kein guter Secret, weil es zu kurz und zu leicht zu erraten ist. Für das Praktikum reicht es als einfaches gemeinsames Test-Secret. In der Praxis würde man einen langen zufälligen Wert verwenden.

## 8. swanctl Konfiguration auf gwsec

Auf `gwsec` wurde diese Datei erstellt:

```bash
cat > /home/secpgast/Abgaben/13/swanctl.conf <<'EOF'
connections {
  secp {
    version = 2
    local_addrs = 10.153.210.1
    remote_addrs = 10.153.210.2
    proposals = aes128-sha256-modp1024
    unique = replace

    local {
      auth = psk
      id = @gwsec
    }

    remote {
      auth = psk
      id = @pcsec1
    }

    children {
      secp-child {
        mode = tunnel
        local_ts = 10.153.210.1/32
        remote_ts = 10.153.210.2/32
        esp_proposals = aes128-sha256
        start_action = start
      }
    }
  }
}

secrets {
  ike-secp {
    id-1 = @gwsec
    id-2 = @pcsec1
    secret = "12345678"
  }
}
EOF

ln -sf /home/secpgast/Abgaben/13/swanctl.conf /etc/swanctl/swanctl.conf
```

### Erklärung der gwsec Konfiguration

```text
connections {
```

Hier beginnt der Block für alle IPsec Verbindungen.

```text
secp {
```

Das ist der Name der Verbindung. Wir haben sie `secp` genannt, passend zum Praktikum.

```text
version = 2
```

Damit wird IKEv2 verwendet. IKEv2 ist moderner als IKEv1 und wird in neuen Setups bevorzugt.

```text
local_addrs = 10.153.210.1
```

Das ist die lokale IP-Adresse von `gwsec`.

```text
remote_addrs = 10.153.210.2
```

Das ist die IP-Adresse der Gegenseite, also `pcsec1`.

```text
proposals = aes128-sha256-modp1024
```

Das ist der IKE Proposal. Er legt fest, welche kryptographischen Verfahren für die IKE Security Association verwendet werden.

| Teil | Bedeutung |
|---|---|
| `aes128` | AES mit 128 Bit für Verschlüsselung |
| `sha256` | SHA-256 für Integrität |
| `modp1024` | Diffie-Hellman Gruppe mit 1024 Bit |

```text
unique = replace
```

Wenn bereits eine Verbindung mit demselben Namen existiert, wird sie ersetzt. Das verhindert, dass alte Verbindungen dauerhaft bestehen bleiben.

```text
local {
  auth = psk
  id = @gwsec
}
```

Dieser Block beschreibt die lokale Seite. `gwsec` authentifiziert sich mit einem Pre-Shared Key und verwendet die Identität `@gwsec`.

```text
remote {
  auth = psk
  id = @pcsec1
}
```

Dieser Block beschreibt die Gegenseite. Die Gegenseite muss sich als `@pcsec1` authentifizieren und ebenfalls denselben Pre-Shared Key kennen.

```text
children {
  secp-child {
```

Eine Child-SA ist die eigentliche IPsec Verbindung für den Nutzdatenverkehr. IKE baut zuerst eine IKE-SA auf, danach wird eine Child-SA für ESP aufgebaut.

```text
mode = tunnel
```

Der Tunnel Mode bedeutet, dass der Verkehr in einen IPsec Tunnel gelegt wird. Für eine VPN Aufgabe ist das passender als Transport Mode.

```text
local_ts = 10.153.210.1/32
remote_ts = 10.153.210.2/32
```

`local_ts` und `remote_ts` sind Traffic Selectors. Sie legen fest, welcher Verkehr geschützt werden soll.

Auf `gwsec` bedeutet das:

```text
lokal:  10.153.210.1/32
remote: 10.153.210.2/32
```

Also genau der Verkehr zwischen `gwsec` und `pcsec1`.

```text
esp_proposals = aes128-sha256
```

Das ist der Proposal für ESP. ESP schützt den eigentlichen Nutzdatenverkehr.

```text
start_action = start
```

Damit versucht strongSwan, die Child-SA automatisch zu starten, sobald die Konfiguration geladen wird.

```text
secrets {
  ike-secp {
    id-1 = @gwsec
    id-2 = @pcsec1
    secret = "12345678"
  }
}
```

Dieser Block definiert den Pre-Shared Key. Beide Identitäten `@gwsec` und `@pcsec1` verwenden denselben Secret `12345678`.

### Warum ist die Konfiguration spiegelverkehrt?

Das war ein wichtiger Punkt bei der Fehlersuche. Als auf `pcsec1` versehentlich die falsche Richtung geladen war, zeigte `swanctl --list-sas` eine lokale Adresse von `10.153.210.1`. Das war ein Hinweis, dass auf `pcsec1` noch die `gwsec` Sicht aktiv war.

Direkt nach `systemctl restart strongswan` ist der `charon` Daemon manchmal noch nicht vollständig bereit. Wenn man `swanctl --load-all` zu früh ausführt, kann dieser Fehler auftreten:


Das bedeutet nicht, dass die Konfigurationsdatei falsch ist. Es bedeutet nur, dass `swanctl` noch keine Verbindung zum VICI Socket von `charon` herstellen konnte.

Mit `sleep 2` wartet man zwei Sekunden, bis `charon` bereit ist.

## 17. tcpdump Prüfung auf gwsec

Auf `gwsec` wurde zusätzlich mit `tcpdump` geprüft, ob ESP Pakete sichtbar sind:

```bash
tcpdump -ni ens7 host 10.153.210.2
```

Dabei wurden ESP Pakete gesehen:

```text
IP 10.153.210.2 > 10.153.210.1: ESP(spi=0xc4ba6663,seq=0x4), length 136
IP 10.153.210.1 > 10.153.210.2: ESP(spi=0xcc0a0d58,seq=0x4), length 136
```

### Warum ist ESP wichtig?

Wenn `tcpdump` ESP Pakete sieht, bedeutet das, dass IPsec tatsächlich verwendet wird. Normaler ICMP Verkehr wäre einfach als `ICMP echo request` sichtbar. ESP zeigt dagegen, dass der Verkehr verschlüsselt beziehungsweise geschützt transportiert wird.

Auf einem Host kann `tcpdump` manchmal zusätzlich entschlüsselte Pakete sehen, weil der Kernel Pakete nach der IPsec Verarbeitung wieder lokal bereitstellt. Deshalb ist es nicht automatisch falsch, wenn man auch ICMP sieht. Wichtig ist, dass ESP Pakete vorhanden sind und die IPsec SA Pakete zählt.

## 18. Anzeige der IPsec Policies

Mit folgendem Befehl wurden die installierten IPsec Policies angezeigt:

```bash
ip xfrm policy
```

Auf `pcsec1` sah die relevante Ausgabe so aus:

```text
src 10.153.210.1/32 dst 10.153.210.2/32
        dir fwd priority 183616 ptype main
        tmpl src 10.153.210.1 dst 10.153.210.2
                proto esp reqid 1 mode tunnel
src 10.153.210.1/32 dst 10.153.210.2/32
        dir in priority 183616 ptype main
        tmpl src 10.153.210.1 dst 10.153.210.2
                proto esp reqid 1 mode tunnel
src 10.153.210.2/32 dst 10.153.210.1/32
        dir out priority 183616 ptype main
        tmpl src 10.153.210.2 dst 10.153.210.1
                proto esp reqid 1 mode tunnel
```

### Was macht ip xfrm policy?

`ip xfrm policy` zeigt, welcher Verkehr vom Kernel durch IPsec geschützt werden soll.

Eine Policy besteht aus:

| Feld | Bedeutung |
|---|---|
| `src` | Quelladresse des Verkehrs |
| `dst` | Zieladresse des Verkehrs |
| `dir` | Richtung, zum Beispiel `in`, `out` oder `fwd` |
| `proto esp` | Der Verkehr soll mit ESP geschützt werden |
| `mode tunnel` | IPsec Tunnel Mode |
| `reqid` | Zuordnung zur Security Association |

### Rolle der Policies

Policies entscheiden, welche Pakete durch IPsec laufen müssen.

Wenn ein Paket von `10.153.210.2` nach `10.153.210.1` geht, passt es auf die `out` Policy. Der Kernel verschlüsselt es mit ESP.

Wenn ein Paket von `10.153.210.1` nach `10.153.210.2` zurückkommt, passt es auf die `in` Policy. Der Kernel entschlüsselt es und prüft die Authentizität.

Mit folgendem Befehl wurden die installierten IPsec States angezeigt:

```bash
ip xfrm state
```

Beispielhafte Ausgabe:

```text
src 10.153.210.2 dst 10.153.210.1
        proto esp spi 0xc4ba6663 reqid 1 mode tunnel
        replay-window 0 flag af-unspec
        auth-trunc hmac(sha256) 0x59dd7221bd7a783bbf977b8bfdf1f23153c8bbf0c28d9f9941785236d4d96b3b 128
        enc cbc(aes) 0x96c030d9d5943e4a2debe9dd61c02bca
```

### Was macht ip xfrm state?

`ip xfrm state` zeigt, wie der Verkehr konkret geschützt wird.

Dort sieht man:

| Feld | Bedeutung |
|---|---|
| `src` und `dst` | Endpunkte der IPsec SA |
| `proto esp` | ESP wird verwendet |
| `spi` | Security Parameter Index |
| `reqid` | Verbindung zur Policy |
| `mode tunnel` | Tunnel Mode |
| `auth-trunc hmac(sha256)` | Authentifizierungsalgorithmus |
| `enc cbc(aes)` | Verschlüsselungsalgorithmus |

### Unterschied zwischen policy und state

Kurz gesagt:

```text
ip xfrm policy: Welcher Verkehr soll geschützt werden?
ip xfrm state: Wie wird dieser Verkehr kryptographisch geschützt?
```

Die Policy ist also die Regel. Der State ist die konkrete kryptographische Umsetzung.

## 20. Fehlersuche: NO_PROPOSAL_CHOSEN

Während der Einrichtung trat mehrfach dieser Fehler auf:

## 24. Fehlersuche: doppelte Child-SAs

Manchmal wurden zwei Child-SAs angezeigt:

```text
secp-child: #1
secp-child: #2
```

Das passierte, weil in der Konfiguration stand:

```text
start_action = start
```

und danach zusätzlich manuell ausgeführt wurde:

```bash
swanctl --initiate --child secp-child
```

Dadurch wurde eine Child-SA automatisch gestartet und eine zweite manuell erstellt.

### Lösung

Für eine saubere Ausgabe sollte man entweder:

1. `start_action = start` verwenden und nicht zusätzlich manuell initiieren.
2. `start_action = trap` verwenden und dann manuell mit `swanctl --initiate --child secp-child` starten.

Für den Test wurde empfohlen:

```bash
swanctl --terminate --ike secp 2>/dev/null || true
ip xfrm state flush
ip xfrm policy flush
systemctl restart strongswan
sleep 2
swanctl --load-all
```

Dann prüfen:

```bash
swanctl --list-sas
```

Falls keine SA aktiv ist, genau einmal auf `pcsec1` starten:

```bash
swanctl --initiate --child secp-child
```

Danach nicht erneut initiieren.

## 26. Theorieantwort für die Abgabe

Die installierten IPsec Policies können mit folgendem Befehl angezeigt werden:

```bash
ip xfrm policy
```

Die Policies legen fest, welcher Netzwerkverkehr durch IPsec geschützt werden soll. Sie enthalten Selektoren wie Quelladresse, Zieladresse und Richtung, zum Beispiel `in`, `out` oder `fwd`.

In unserem Fall gibt es Policies für den Verkehr zwischen `pcsec1` und `gwsec`. Wenn ein Paket zu einer solchen Policy passt, verarbeitet der Linux Kernel es über IPsec. Ausgehender Verkehr wird verschlüsselt und authentifiziert. Eingehender Verkehr wird entschlüsselt und überprüft.

Die konkreten kryptographischen Zustände können mit folgendem Befehl angezeigt werden:

```bash
ip xfrm state
```

Dort sieht man unter anderem ESP, SPI-Werte, verwendete Algorithmen, Schlüsselmaterial und den Tunnel Mode.

Kurz gesagt:

```text
Policies entscheiden, welcher Verkehr geschützt werden soll.
States beschreiben, wie dieser Verkehr konkret geschützt wird.
```

## 27. Was wir am Ende erreicht haben

Am Ende war die IPsec Verbindung korrekt eingerichtet:

```text
pcsec1 10.153.210.2  <==== IPsec Tunnel ESP ====>  gwsec 10.153.210.1
```

Die wichtigsten Nachweise waren:

1. `swanctl --list-conns` zeigte auf beiden Seiten die richtige lokale und entfernte Adresse.
2. `swanctl --list-sas` zeigte `ESTABLISHED`.
3. Die Child-SA war `INSTALLED, TUNNEL`.
4. Nach einem Ping wurden Bytes und Pakete in der Child-SA gezählt.
5. `tcpdump` auf `gwsec` zeigte ESP Pakete.
6. `ip xfrm policy` zeigte passende Policies für `in`, `out` und `fwd`.
7. `ip xfrm state` zeigte die konkreten ESP Security Associations.

## 28. Wichtige Takeaways

- `swanctl.conf` muss auf beiden Seiten existieren.
- Die lokale und entfernte IP müssen auf beiden Seiten spiegelverkehrt sein.
- Der Pre-Shared Key muss auf beiden Seiten identisch sein.
- `swanctl --load-all` lädt nur die Datei in den laufenden Daemon, es startet nicht automatisch immer dauerhaft nach jedem Restart.
- Nach `systemctl restart strongswan` sollte man kurz warten und dann `swanctl --load-all` ausführen.
- `swanctl --list-conns` zeigt geladene Konfigurationen.
- `swanctl --list-sas` zeigt aktive Tunnel.
- `ip xfrm policy` zeigt, welcher Verkehr geschützt werden soll.
- `ip xfrm state` zeigt, wie der Verkehr kryptographisch geschützt wird.
- ESP Pakete in `tcpdump` sind ein guter Hinweis, dass IPsec tatsächlich verwendet wird.
- Mehrere Child-SAs entstehen, wenn man `start_action = start` nutzt und zusätzlich manuell initiiert.
