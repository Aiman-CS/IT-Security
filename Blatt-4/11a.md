# Aufgabe 11(a): OpenSSL CA Setup on `pcsec1`
passwort cert: 12345678
## Goal of the task

The goal of Aufgabe 11(a) was to create a small local Certificate Authority (CA) on `pcsec1` under:

```bash
/home/secpgast/Abgaben/11/
```

The task required the following:

- Create the directories `keys`, `private`, and `newcerts`.
- Create an OpenSSL configuration file named `openssl.cnf`.
- Create a self-signed X.509 CA certificate.
- The CA certificate must be valid for 10 years.
- The corresponding private RSA key must be 2048 bit long.
- The private key must be encrypted with AES256.
- Store the private CA key as:

```bash
/home/secpgast/Abgaben/11/private/cakey.pem
```

- Store the CA certificate as:

```bash
/home/secpgast/Abgaben/11/cacert.pem
```

The certificate had to contain the following subject information:

```text
Country Name: DE
State or Province Name: Bavaria
Locality Name: Munich
Organization Name: LMU IFI SecP Gruppe 09
Common Name: LMU IFI SecP Gruppe 09 CA
Email Address: mana.jaqoubi@campus.lmu.de
```

## 1. Installing OpenSSL

At first, OpenSSL was not installed:

```bash
openssl version
```

Result:

```text
-bash: openssl: command not found
```

So we tried to install it with `apt`:

```bash
apt update
apt install openssl -y
```

This failed because the VM could not resolve `archive.debian.org`:

```text
Temporary failure resolving 'archive.debian.org'
```

The reason was not an OpenSSL problem. The VM had no working route to the internet for package downloads.

We checked IPv4 connectivity:

```bash
ping -c 2 8.8.8.8
```

Result:

```text
connect: Network is unreachable
```

Then we checked the current IPv4 route:

```bash
ip route
```

Result:

```text
10.153.210.0/29 dev ens7 proto kernel scope link src 10.153.210.2
```

This showed that the VM only had a local IPv4 route and no default IPv4 route.

The VM did have an IPv6 address on `ens2`:

```text
inet6 2001:db6::3/64 scope global
```

The neighbor table also showed an IPv6 router:

```text
2001:db6::ff dev ens2 lladdr fe:54:00:11:8e:3c router REACHABLE
```

Therefore, we added an IPv6 default route:

```bash
ip -6 route add default via 2001:db6::ff dev ens2
```

We also restored the lab DNS server in `/etc/resolv.conf`:

```bash
echo "nameserver 2001:4ca0::53:1" > /etc/resolv.conf
```

Then we tested IPv6 connectivity:

```bash
ping6 -c 2 2001:db6::ff
ping6 -c 2 2001:4ca0::53:1
ping6 -c 2 archive.debian.org
```

The test worked. `archive.debian.org` resolved and was reachable over IPv6:

```text
64 bytes from 2a04:4e42:200::644: icmp_seq=1 ttl=57 time=10.4 ms
64 bytes from 2a04:4e42:200::644: icmp_seq=2 ttl=57 time=10.3 ms
```

Then we installed OpenSSL by forcing `apt` to use IPv6:

```bash
apt -o Acquire::ForceIPv6=true update
apt -o Acquire::ForceIPv6=true install openssl -y
```

The installation succeeded:

```text
Setting up openssl (1.1.0l-1~deb9u6) ...
```

Why this was necessary:

- The VM could not use IPv4 for external internet access.
- The lab DNS server was reachable via IPv6.
- `archive.debian.org` was reachable via IPv6.
- Therefore, OpenSSL had to be installed using IPv6.

## 2. Creating the directory structure

We set the base directory for the task:

```bash
BASE=/home/secpgast/Abgaben/11
```

Then we created the required directories:

```bash
mkdir -p $BASE/keys $BASE/private $BASE/newcerts
chmod 700 $BASE/private
```

Why these directories were created:

### `keys`

This directory is used to store private or public keys for later certificates. It is required by the assignment and will also be used in later subtasks, for example Aufgabe 11(c).

### `private`

This directory stores the private CA key:

```bash
private/cakey.pem
```

This key is the most sensitive file in the whole CA setup. Anyone who has access to this key and its passphrase could sign certificates as this CA. That is why we set restrictive permissions with:

```bash
chmod 700 $BASE/private
```

### `newcerts`

This directory is used by OpenSSL to store newly issued certificates. It is required by the assignment and will also be used in later subtasks.

## 3. Creating CA database files

We also created the OpenSSL CA database files:

```bash
touch $BASE/index.txt
echo 1000 > $BASE/serial
echo 1000 > $BASE/crlnumber
```

Why these files were created:

### `index.txt`

This is the OpenSSL CA database. It keeps track of issued and revoked certificates.

### `serial`

This file stores the next serial number for certificates issued by the CA. We started at `1000`.

### `crlnumber`

This file stores the next number for Certificate Revocation Lists, also called CRLs. It will be needed later for Aufgabe 11(g), where a CRL has to be created.

Even though Aufgabe 11(a) mainly asks for the CA certificate, these files are important because later subtasks use the CA to sign and revoke certificates.

## 5. Explanation of the OpenSSL configuration

### `[ ca ]`

```ini
[ ca ]
default_ca = CA_default
```

This tells OpenSSL which CA configuration section should be used by default. In this case, OpenSSL should use the section called `[ CA_default ]`.

---

### `[ CA_default ]`

```ini
dir               = /home/secpgast/Abgaben/11
```

This defines the base directory of the CA setup. All other file paths are built relative to this directory.

```ini
certs             = $dir/newcerts
new_certs_dir     = $dir/newcerts
```

These define where OpenSSL stores newly issued certificates.

```ini
database          = $dir/index.txt
serial            = $dir/serial
crlnumber         = $dir/crlnumber
crl               = $dir/crl.pem
```

These define the CA database, serial number file, CRL number file, and CRL output file.

```ini
certificate       = $dir/cacert.pem
private_key       = $dir/private/cakey.pem
```

These tell OpenSSL where the CA certificate and the CA private key are located.

```ini
default_md        = sha256
```

This sets SHA-256 as the default message digest. SHA-256 is used instead of outdated hashes such as MD5 or SHA-1 for certificate signatures.

```ini
default_days      = 365
```

This is the default validity period for certificates issued later by the CA. For Aufgabe 11(a), we explicitly used `-days 3650`, because the CA certificate had to be valid for 10 years.

```ini
default_crl_days  = 30
```

This sets the default validity period for CRLs to 30 days.

```ini
policy            = policy_match
```

This tells OpenSSL to use the `[ policy_match ]` section when signing certificates.

---

### `[ policy_match ]`

```ini
countryName             = match
stateOrProvinceName     = match
organizationName        = match
commonName              = supplied
```

This section defines which subject fields must match the CA certificate when signing other certificates.

For example:

- `countryName = match` means issued certificates must use the same country as the CA.
- `stateOrProvinceName = match` means issued certificates must use the same state or province as the CA.
- `organizationName = match` means issued certificates must use the same organization as the CA.
- `commonName = supplied` means a Common Name must be provided.

This is useful for later subtasks where the CA signs other certificates.

---

### `[ req ]`

```ini
default_bits        = 2048
```

This sets the default RSA key size to 2048 bits, matching the assignment requirement.

```ini
default_md          = sha256
```

This sets SHA-256 as the default digest for certificate requests.

```ini
distinguished_name  = req_distinguished_name
```

This tells OpenSSL where the certificate subject information is defined.

```ini
x509_extensions     = v3_ca
```

This tells OpenSSL to use the `[ v3_ca ]` extension section when creating a self-signed X.509 certificate.

```ini
prompt              = no
```

This disables interactive prompts for subject fields. Instead, OpenSSL takes the certificate information directly from `[ req_distinguished_name ]`.

```ini
string_mask         = utf8only
```

This ensures that strings are encoded as UTF-8.

---

### `[ req_distinguished_name ]`

```ini
C  = DE
ST = Bavaria
L  = Munich
O  = LMU IFI SecP Gruppe 09
CN = LMU IFI SecP Gruppe 09 CA
emailAddress = mana.jaqoubi@campus.lmu.de
```

This section contains the required identity information for the CA certificate.

It directly matches the assignment requirements:

- Country Name: `DE`
- State or Province Name: `Bavaria`
- Locality Name: `Munich`
- Organization Name: `LMU IFI SecP Gruppe 09`
- Common Name: `LMU IFI SecP Gruppe 09 CA`
- Email Address: `mana.jaqoubi@campus.lmu.de`

The Common Name includes `CA` because this certificate represents the Certificate Authority itself, not a normal server or client certificate.

---

### `[ v3_ca ]`

```ini
subjectKeyIdentifier   = hash
```

This creates a unique identifier for the CA public key.

```ini
authorityKeyIdentifier = keyid:always,issuer
```

This links the certificate to the authority that issued it. Since this is a self-signed CA certificate, the issuer is the CA itself.

```ini
basicConstraints       = critical, CA:true
```

This is one of the most important lines. It marks the certificate as a CA certificate.

`CA:true` means this certificate is allowed to act as a Certificate Authority and sign other certificates.

```ini
keyUsage               = critical, keyCertSign, cRLSign
```

This defines what the CA key may be used for:

- `keyCertSign`: the CA may sign certificates.
- `cRLSign`: the CA may sign Certificate Revocation Lists.

This is required because later subtasks use this CA to sign and revoke certificates.

## 6. First attempt to create the CA key and certificate

We first tried to create the encrypted CA key and certificate in one command:

```bash
openssl req \
  -config openssl.cnf \
  -new \
  -x509 \
  -days 3650 \
  -newkey rsa:2048 \
  -aes256 \
  -extensions v3_ca \
  -keyout private/cakey.pem \
  -out cacert.pem
```

This failed with:

```text
req: Unknown digest aes256
req: Use -help for summary.
```

Why this happened:

The installed OpenSSL version is old:

```text
OpenSSL 1.1.0l-1~deb9u6
```

In this version, the `openssl req` command did not accept `-aes256` in the way we tried to use it. It interpreted `aes256` incorrectly as a digest option.

Therefore, we split the process into two steps:

1. Generate the encrypted CA private key.
2. Generate the self-signed CA certificate using that key.

This is cleaner and works reliably on this OpenSSL version.

## 7. Creating the AES256-encrypted 2048-bit RSA private CA key

We removed any failed or incomplete old files:

```bash
rm -f private/cakey.pem cacert.pem
```

```bash
openssl genrsa -aes256 -out private/cakey.pem 2048
```

Why this command was used:

```bash
openssl genrsa
```

This generates an RSA private key.

```bash
-aes256
```

This encrypts the private key with AES256, which is explicitly required by the assignment.

```bash
-out private/cakey.pem
```

This stores the private CA key at the exact required path.

```bash
2048
```

This creates a 2048-bit RSA key, which is also required by the assignment.

The passphrase protects the private key. Whenever the CA key is used later, OpenSSL asks for the passphrase.

## 8. Creating the self-signed CA certificate

After creating the private key, we created the self-signed CA certificate:

```bash
openssl req \
  -config openssl.cnf \
  -new \
  -x509 \
  -days 3650 \
  -key private/cakey.pem \
  -extensions v3_ca \
  -out cacert.pem
```

OpenSSL asked for the passphrase of the encrypted CA key:

```text
Enter pass phrase for private/cakey.pem:
```

Why this command was used:

```bash
openssl req
```

This creates a certificate request or a certificate depending on the options.

```bash
-config openssl.cnf
```

This tells OpenSSL to use our custom CA configuration.

```bash
-new
```

This creates a new request internally.

```bash
-x509
```

This makes OpenSSL create a self-signed X.509 certificate instead of only creating a CSR.

```bash
-days 3650
```

This sets the validity to 3650 days, which is approximately 10 years. This matches the assignment.

```bash
-key private/cakey.pem
```

This uses the CA private key we created before.

```bash
-extensions v3_ca
```

This applies the CA extensions from the `[ v3_ca ]` section, especially `CA:true`, `keyCertSign`, and `cRLSign`.

```bash
-out cacert.pem
```

This stores the CA certificate at the required path.

## 9. Verifying the CA certificate

We verified the CA certificate with:

```bash
openssl x509 -in cacert.pem -noout -subject -issuer -dates
```

Result:

```text
subject=C = DE, ST = Bavaria, L = Munich, O = LMU IFI SecP Gruppe 09, CN = LMU IFI SecP Gruppe 09 CA, emailAddress = mana.jaqoubi@campus.lmu.de
issuer=C = DE, ST = Bavaria, L = Munich, O = LMU IFI SecP Gruppe 09, CN = LMU IFI SecP Gruppe 09 CA, emailAddress = mana.jaqoubi@campus.lmu.de
notBefore=May 18 08:56:34 2026 GMT
notAfter=May 15 08:56:34 2036 GMT
```

Why this confirms success:

### The subject is correct

The subject contains exactly the required CA identity information:

```text
C = DE
ST = Bavaria
L = Munich
O = LMU IFI SecP Gruppe 09
CN = LMU IFI SecP Gruppe 09 CA
emailAddress = mana.jaqoubi@campus.lmu.de
```

### The certificate is self-signed

The `subject` and `issuer` are identical:

```text
subject = LMU IFI SecP Gruppe 09 CA
issuer  = LMU IFI SecP Gruppe 09 CA
```

That means the CA certificate signed itself, which is exactly what a self-signed root CA certificate does.

### The certificate is valid for about 10 years

The certificate is valid from:

```text
May 18 2026
```

until:

```text
May 15 2036
```

This is approximately 10 years, as required.

## 10. Verifying the CA private key

We checked the private key with:

```bash
openssl rsa -in private/cakey.pem -check
```

OpenSSL asked for the passphrase:

```text
Enter pass phrase for private/cakey.pem:
```

Result:

```text
RSA key ok
writing RSA key
```

This confirmed that the private key is valid.

Important security note:

The command above also printed the private key to the terminal. For documentation, the actual private key must not be copied into the Markdown file or shared anywhere.

A safer verification command is:

```bash
openssl rsa -in private/cakey.pem -check -noout
```

This checks the key without printing the private key content.

## 14. Security note

The file `private/cakey.pem` is the private key of the CA. It must stay secret.

Do not paste it into reports, chats, emails, Git repositories, or screenshots.

Only the CA certificate `cacert.pem` is public. The private CA key is not public.
