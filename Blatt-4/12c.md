# Aufgabe 12(c): CA in den Browser importieren und HTTPS-Konfiguration prüfen

## Ziel der Aufgabe

In Aufgabe 12(c) soll geprüft werden, ob die HTTPS-Konfiguration aus Aufgabe 12(b) korrekt funktioniert.

Die Aufgabe verlangt, dass die eigene CA in einen Browser importiert wird. Danach soll der Webserver über folgende Adresse erreichbar sein:

```text
https://gruppe09.secp.lab.nm.ifi.lmu.de
```

Dabei soll die Verbindung von einem IPv6-fähigen Client aus dem Münchner Wissenschaftsnetz, kurz MWN, erfolgen.

Beispiele dafür sind:

```text
CIP-Pool der LMU
Cisco AnyConnect VPN des LRZ
```

---

## Warum müssen wir die CA in den Browser importieren?

In Aufgabe 11 wurde eine eigene Certificate Authority, kurz CA, erstellt.

Diese CA heißt bei uns:

```text
LMU IFI SecP Gruppe 09 CA
```

Sie hat das Server-Zertifikat für Apache signiert.

Das Server-Zertifikat gehört zu:

```text
gruppe09.secp.lab.nm.ifi.lmu.de
```

Ein normaler Browser vertraut unserer selbst erstellten CA aber nicht automatisch.

Browser vertrauen standardmäßig nur bekannten öffentlichen CAs, zum Beispiel großen Zertifizierungsstellen, die bereits im Betriebssystem oder im Browser hinterlegt sind.

Unsere Übungs-CA ist privat und lokal erstellt. Deshalb kennt der Browser sie noch nicht.

Wenn man die CA nicht importiert, zeigt der Browser wahrscheinlich eine Warnung wie:

```text
Verbindung ist nicht sicher
Zertifikat ist nicht vertrauenswürdig
Unknown issuer
```

Das bedeutet nicht unbedingt, dass das Zertifikat falsch ist. Es bedeutet nur:

```text
Der Browser kennt die ausstellende CA noch nicht.
```

Deshalb muss `cacert.pem` in den Browser importiert und als vertrauenswürdige CA markiert werden.

---

## Was ist eine CA?

CA steht für:

```text
Certificate Authority
```

Auf Deutsch:

```text
Zertifizierungsstelle
```

Eine CA signiert Zertifikate.

In unserem Fall hat unsere eigene CA das Apache-Zertifikat signiert.

Die CA-Datei liegt auf `pcsec1` hier:

```bash
/home/secpgast/Abgaben/11/cacert.pem
```

Diese Datei ist öffentlich und darf in den Browser importiert werden.

Wichtig:

```text
cacert.pem darf kopiert und importiert werden.
private/cakey.pem darf niemals kopiert oder weitergegeben werden.
```

---

## Was ist der Unterschied zwischen CA-Zertifikat und Server-Zertifikat?

## CA-Zertifikat

Das CA-Zertifikat ist:

```bash
cacert.pem
```

Es sagt:

```text
Das ist die Zertifizierungsstelle, der vertraut werden soll.
```

Dieses Zertifikat wird in den Browser importiert.

---

## Server-Zertifikat

Das Server-Zertifikat ist:

```bash
apache2.pem
```

Es sagt:

```text
Dieser Server ist gruppe09.secp.lab.nm.ifi.lmu.de.
```

Dieses Zertifikat liegt auf `pcsec2` und wird von Apache beim HTTPS-Verbindungsaufbau präsentiert.

---

## Private Key

Der private Schlüssel von Apache ist:

```bash
apache2.key
```

Er liegt auf `pcsec2` unter:

```bash
/etc/ssl/secp/apache2.key
```

Dieser Schlüssel darf nicht in den Browser importiert werden.

Der Browser braucht nur die CA, nicht den privaten Schlüssel des Servers.

---

# 1. Voraussetzungen prüfen

Bevor man mit dem Browser testet, sollte geprüft werden, ob Apache und HTTPS bereits funktionieren.

Auf `pcsec2`:

```bash
service apache2 status
```

## Erklärung

Der Befehl prüft, ob der Apache-Dienst läuft.

Wichtiges Ergebnis:

```text
Active: active (running)
```

Das bedeutet:

```text
Apache läuft.
```

---

## Prüfen, ob Apache auf Port 443 lauscht

Auf `pcsec2`:

```bash
ss -tlnp | grep ':443'
```

## Erklärung

### `ss`

`ss` zeigt aktive Netzwerk-Sockets an.

### `-t`

Zeigt TCP-Sockets.

### `-l`

Zeigt nur Dienste, die auf Verbindungen warten.

### `-n`

Zeigt IP-Adressen und Ports numerisch an.

### `-p`

Zeigt den Prozess, der den Port verwendet.

### `grep ':443'`

Filtert die Ausgabe auf Port `443`.

Erwartetes Ergebnis:

```text
LISTEN ... :::443 ... apache2
```

Das bedeutet:

```text
Apache wartet auf HTTPS-Verbindungen auf Port 443.
```

---

# 2. Zertifikat lokal mit OpenSSL prüfen

Bevor man den Browser nutzt, kann man die Zertifikatskette mit OpenSSL testen.

Auf `pcsec2` wurde dieser Befehl verwendet:

```bash
openssl s_client \
  -connect localhost:443 \
  -servername gruppe09.secp.lab.nm.ifi.lmu.de \
  -CAfile /etc/ssl/secp/cacert.pem
```

---

## Erklärung des Befehls

### `openssl s_client`

`openssl s_client` baut eine TLS-Verbindung zu einem Server auf.

Damit kann man testen:

```text
Wird ein Zertifikat ausgeliefert?
Ist die Zertifikatskette korrekt?
Kann die Verbindung verschlüsselt aufgebaut werden?
Welcher Cipher wird genutzt?
```

---

### `-connect localhost:443`

Der Client verbindet sich mit Port `443` auf dem lokalen System.

Da der Befehl auf `pcsec2` ausgeführt wird, bedeutet `localhost`:

```text
pcsec2 selbst
```

---

### `-servername gruppe09.secp.lab.nm.ifi.lmu.de`

Das setzt den SNI-Namen.

SNI steht für:

```text
Server Name Indication
```

Damit sagt der Client dem Server, für welchen Hostnamen er ein Zertifikat erwartet.

Das ist wichtig, weil ein Server mehrere HTTPS-Seiten mit verschiedenen Zertifikaten betreiben kann.

---

### `-CAfile /etc/ssl/secp/cacert.pem`

Damit wird unsere eigene CA als vertrauenswürdige CA verwendet.

Ohne diesen Parameter würde OpenSSL unserer eigenen Übungs-CA nicht automatisch vertrauen.

---

## Erfolgreiches Ergebnis

Bei uns war wichtig:

```text
Verification: OK
Verify return code: 0 (ok)
```

Das bedeutet:

```text
Das Zertifikat wurde erfolgreich gegen unsere CA geprüft.
Die HTTPS-Konfiguration auf Apache funktioniert.
```

---

# 3. Prüfen, ob das Zertifikat den richtigen Namen und die IP-Adressen enthält

Die Aufgabe verlangt, dass das Zertifikat auf diesen Namen ausgestellt ist:

```text
gruppe09.secp.lab.nm.ifi.lmu.de
```

Außerdem müssen die IPv4- und IPv6-Adresse von `pcsec2` enthalten sein.

Die Werte waren:

```text
IPv4: 10.153.210.3
IPv6: 2001:4ca0:4001:f21::3
```

Auf `pcsec2` prüfen:

```bash
openssl x509 -in /etc/ssl/secp/apache2.pem -noout -text | grep -A 5 "Subject Alternative Name"
```

## Erklärung

### `openssl x509`

Liest und analysiert ein X.509-Zertifikat.

### `-in /etc/ssl/secp/apache2.pem`

Das ist das Server-Zertifikat, das Apache verwendet.

### `-noout`

Das Zertifikat wird nicht komplett im PEM-Format ausgegeben.

### `-text`

Das Zertifikat wird menschenlesbar angezeigt.

### `grep -A 5 "Subject Alternative Name"`

Sucht den Abschnitt mit den Subject Alternative Names und zeigt zusätzlich fünf Zeilen danach an.

---

## Erwartetes Ergebnis

Man sollte ungefähr Folgendes sehen:

```text
DNS:gruppe09.secp.lab.nm.ifi.lmu.de
IP Address:10.153.210.3
IP Address:2001:4CA0:4001:F21:0:0:0:3
```

Wichtig:

```text
2001:4ca0:4001:f21::3
```

kann in der langen Schreibweise angezeigt werden als:

```text
2001:4CA0:4001:F21:0:0:0:3
```

Das ist dieselbe IPv6-Adresse.

# 4. CA-Zertifikat vom Server auf den eigenen Rechner kopieren

Damit der Browser der CA vertrauen kann, braucht man die Datei:

```bash
/home/secpgast/Abgaben/11/cacert.pem
```

Diese Datei liegt auf `pcsec1`.

Man kann sie auf den eigenen Rechner kopieren.

Beispiel von einem lokalen Rechner aus:

```bash
scp -P 9002 root@gruppe09.secp.lab.nm.ifi.lmu.de:/home/secpgast/Abgaben/11/cacert.pem ./gruppe09-ca.pem
```

---

## Erklärung des Befehls

### `scp`

`scp` kopiert Dateien über SSH.

### `-P 9002`

Der SSH-Port für `pcsec1` ist in der Praktikumsumgebung Port `9002`.

### `root@gruppe09.secp.lab.nm.ifi.lmu.de`

Das ist der SSH-Zugang zur Gruppe.

### `:/home/secpgast/Abgaben/11/cacert.pem`

Das ist der Pfad der CA-Datei auf `pcsec1`.

### `./gruppe09-ca.pem`

Das ist der Zielname auf dem lokalen Rechner.

Man kann die Datei auch weiterhin `cacert.pem` nennen. Der Name ist für den Browser nicht entscheidend.

---

## Alternative: Datei über Terminal anzeigen und speichern

Falls `scp` nicht genutzt werden kann, kann man die Datei auf `pcsec1` anzeigen:

```bash
cat /home/secpgast/Abgaben/11/cacert.pem
```

Dann kopiert man den kompletten Inhalt inklusive dieser Zeilen:

```text
-----BEGIN CERTIFICATE-----
...
-----END CERTIFICATE-----
```

in eine lokale Datei, zum Beispiel:

```text
gruppe09-ca.pem
```

Wichtig ist, dass Anfang und Ende vollständig enthalten sind.

# 5. CA in Firefox importieren

Firefox verwendet oft einen eigenen Zertifikatsspeicher.

Deshalb muss man die CA direkt in Firefox importieren.

## Schritte in Firefox

1. Firefox öffnen.
2. Einstellungen öffnen.
3. Nach `Zertifikate` suchen.
4. Auf `Zertifikate anzeigen` klicken.
5. Zum Tab `Zertifizierungsstellen` gehen.
6. Auf `Importieren` klicken.
7. Die Datei `gruppe09-ca.pem` oder `cacert.pem` auswählen.
8. Die Option aktivieren:

```text
Dieser CA vertrauen, um Websites zu identifizieren
```

9. Bestätigen.

---

## Warum genau diese Vertrauenseinstellung?

Die CA soll für HTTPS-Websites vertraut werden.

Deshalb muss die Option für Websites aktiviert werden.

Wenn man diese Option nicht aktiviert, ist die CA zwar importiert, aber der Browser vertraut ihr nicht für HTTPS-Verbindungen.

---

# 6. CA in Chrome oder Chromium importieren

Chrome und Chromium verwenden je nach System meistens den Zertifikatsspeicher des Betriebssystems.

Unter Linux kann man Zertifikate auch über die Chrome-Einstellungen importieren.

## Schritte in Chrome oder Chromium

1. Chrome oder Chromium öffnen.
2. Einstellungen öffnen.
3. Nach `Zertifikate verwalten` suchen.
4. Den Bereich für Zertifizierungsstellen öffnen.
5. `Importieren` auswählen.
6. Die Datei `gruppe09-ca.pem` oder `cacert.pem` auswählen.
7. Vertrauen für Websites aktivieren, falls gefragt.
8. Browser neu starten.

---

## Hinweis zu Chrome unter Linux

Je nach Distribution kann Chrome den System-Zertifikatsspeicher verwenden.

Falls der Import im Browser nicht funktioniert, kann man die CA systemweit installieren.

Das ist aber abhängig vom lokalen System und für die Übung meist nicht nötig, wenn Firefox verwendet wird.

Firefox ist für solche Tests oft einfacher, weil der Import direkt im Browser funktioniert.

# 7. Verbindung im Browser testen

Nachdem die CA importiert wurde, öffnet man im Browser:

```text
https://gruppe09.secp.lab.nm.ifi.lmu.de
```

Wichtig:

```text
Der Client muss IPv6-fähig sein.
Der Client muss im Münchner Wissenschaftsnetz sein.
Oder der Client muss über den LRZ Cisco AnyConnect VPN verbunden sein.
```

---

## Warum IPv6?

Die Aufgabenstellung sagt, dass der Zugriff von einem IPv6-fähigen Client im Münchner Wissenschaftsnetz erfolgen kann.

Der Server ist über:

```text
2001:4ca0:4001:f21::3
```

erreichbar.

Das ist eine globale IPv6-Adresse im relevanten Netz.

Wenn der eigene Rechner kein IPv6 im MWN hat, kann die Webseite eventuell nicht direkt geöffnet werden.

---

## Wie prüfe ich, ob mein Client IPv6 hat?

Auf Linux oder macOS:

```bash
ip -6 addr
```

oder:

```bash
ifconfig
```

Man sucht nach einer IPv6-Adresse, die nicht nur mit `fe80::` beginnt.

Auf Windows:

```powershell
ipconfig
```

Auch hier sucht man nach einer IPv6-Adresse außerhalb von `fe80::`.

# 9. Was bedeutet es, wenn der Browser trotzdem warnt?

Wenn der Browser weiterhin eine Zertifikatswarnung anzeigt, gibt es mehrere mögliche Ursachen.

## Ursache 1: CA wurde nicht als vertrauenswürdig importiert

Die CA wurde vielleicht importiert, aber nicht für Websites als vertrauenswürdig markiert.

Lösung:

```text
CA erneut importieren und die Option für Website-Vertrauen aktivieren.
```

---

## Ursache 2: Falscher Hostname

Die URL muss exakt sein:

```text
https://gruppe09.secp.lab.nm.ifi.lmu.de
```

Wenn man stattdessen eine IP-Adresse oder einen anderen Namen verwendet, kann der Browser meckern, falls dieser Name nicht zum Zertifikat passt.

Da wir die IPs ebenfalls als SAN eingetragen haben, sollte auch die IP grundsätzlich im Zertifikat stehen. Trotzdem ist für die Aufgabe der Hostname wichtig.

---

## Ursache 3: Zertifikat enthält keine SANs

Moderne Browser verlassen sich auf Subject Alternative Names.

Deshalb muss das Zertifikat die SANs enthalten.

Prüfung auf `pcsec2`:

```bash
openssl x509 -in /etc/ssl/secp/apache2.pem -noout -text | grep -A 5 "Subject Alternative Name"
```

---

## Ursache 4: Apache nutzt falsches Zertifikat

Apache könnte noch ein anderes Zertifikat geladen haben.

Prüfen:

```bash
grep -R "SSLCertificate" /etc/apache2/sites-enabled/
```

Damit sieht man, welche Zertifikate Apache in den aktivierten Sites verwendet.

---

## Ursache 5: Apache wurde nicht neu gestartet

Nach Änderungen an Zertifikaten oder Konfiguration muss Apache neu gestartet werden:

```bash
service apache2 restart
```

# 11. Warum Aufgabe 12(c) wichtig ist

Aufgabe 12(b) prüft technisch, ob der Server HTTPS kann.

Aufgabe 12(c) prüft aus Sicht eines echten Nutzers:

```text
Kann ein Browser dem Zertifikat vertrauen?
Ist die CA korrekt importiert?
Passt der Hostname zum Zertifikat?
Ist die HTTPS-Verbindung wirklich nutzbar?
```

Das ist wichtig, weil HTTPS nicht nur bedeutet:

```text
Port 443 ist offen.
```

HTTPS bedeutet auch:

```text
Der Client kann die Identität des Servers prüfen.
Die Zertifikatskette ist vertrauenswürdig.
Die Verbindung ist verschlüsselt.
Der Name in der URL passt zum Zertifikat.
```
