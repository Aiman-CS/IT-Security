# Aufgabe 12: Apache-Webserver mit HTTPS und eigener CA

## Ziel der Aufgabe

In Aufgabe 12 sollte auf `pcsec2` ein sicherer Webserver eingerichtet werden.

Die Aufgabe bestand aus zwei praktischen Teilen:

```text
12(a) Apache2 auf pcsec2 installieren.

12(b) Apache auf HTTPS, also Port 443, aktivieren.
      Der Webserver soll ein Maschinen-Zertifikat verwenden.
      Dieses Zertifikat muss von unserer eigenen CA signiert sein.
      Das Zertifikat muss für gruppe09.secp.lab.nm.ifi.lmu.de ausgestellt sein.
      Die IPv4- und IPv6-Adresse von pcsec2 müssen im Zertifikat enthalten sein.
```

Unsere verwendeten Werte:

```text
Hostname: gruppe09.secp.lab.nm.ifi.lmu.de
IPv4:     10.153.210.3
IPv6:     2001:4ca0:4001:f21::3
CA:       LMU IFI SecP Gruppe 09 CA
```

---

## Grundidee

Ein Webserver stellt Webseiten über das Netzwerk bereit. Apache2 ist ein häufig verwendeter Webserver.

HTTP läuft normalerweise auf Port `80`. HTTPS läuft normalerweise auf Port `443`.

HTTPS ist HTTP mit TLS. TLS sorgt für zwei wichtige Dinge:

```text
1. Verschlüsselung der Verbindung
2. Authentisierung des Servers über ein Zertifikat
```

Damit der Browser oder ein anderer Client dem Server vertraut, braucht der Server ein Zertifikat. Dieses Zertifikat muss zu dem Namen passen, unter dem der Server erreichbar ist.

In unserem Fall lautet dieser Name:

```text
gruppe09.secp.lab.nm.ifi.lmu.de
```

Das Zertifikat wurde nicht von einer öffentlichen CA wie Let's Encrypt ausgestellt, sondern von unserer eigenen CA aus Aufgabe 11.

---

## Wichtige Begriffe

### Apache2

Apache2 ist der Webserver, der auf `pcsec2` installiert wurde. Er nimmt HTTP- oder HTTPS-Anfragen entgegen und liefert Inhalte aus, zum Beispiel die Standardseite aus `/var/www/html`.

### HTTPS

HTTPS bedeutet, dass HTTP über TLS abgesichert wird. Der Client baut eine verschlüsselte Verbindung zum Server auf und prüft dabei das Zertifikat des Servers.

### Port 443

Port `443` ist der Standardport für HTTPS. Wenn Apache auf Port `443` lauscht, kann er HTTPS-Verbindungen annehmen.

### Zertifikat

Ein Zertifikat verbindet eine Identität, zum Beispiel einen Hostnamen, mit einem öffentlichen Schlüssel.

Das Server-Zertifikat in dieser Aufgabe sagt sinngemäß:

```text
Der öffentliche Schlüssel gehört zu gruppe09.secp.lab.nm.ifi.lmu.de.
```

### Private Key

Der Private Key ist der geheime Schlüssel des Servers. Er muss zum öffentlichen Schlüssel im Zertifikat passen. Der Private Key darf nicht öffentlich lesbar sein.

Unser Apache Private Key liegt später auf `pcsec2` hier:

```bash
/etc/ssl/secp/apache2.key
```

### CA

CA steht für Certificate Authority. Eine CA signiert Zertifikate. Unsere CA wurde in Aufgabe 11 erstellt.

Wichtige CA-Dateien auf `pcsec1`:

```bash
/home/secpgast/Abgaben/11/cacert.pem
/home/secpgast/Abgaben/11/private/cakey.pem
```

`cacert.pem` ist das öffentliche CA-Zertifikat. `private/cakey.pem` ist der private CA-Schlüssel. Mit diesem privaten CA-Schlüssel signieren wir neue Zertifikate.

### CSR

CSR steht für Certificate Signing Request. Ein CSR ist ein Zertifikatsantrag. Er enthält die Informationen, die später im Zertifikat stehen sollen, zum Beispiel den Common Name und den öffentlichen Schlüssel.

Die CA signiert den CSR und erstellt daraus ein Zertifikat.

### Common Name

Der Common Name, kurz CN, ist der Hauptname des Zertifikats.

Für diese Aufgabe musste der CN sein:

```text
gruppe09.secp.lab.nm.ifi.lmu.de
```

### Subject Alternative Name

Subject Alternative Name, kurz SAN, ist heute besonders wichtig. Moderne TLS-Clients prüfen den Servernamen meistens über SAN und nicht nur über den Common Name.

In dieser Aufgabe mussten dort stehen:

```text
DNS: gruppe09.secp.lab.nm.ifi.lmu.de
IP:  10.153.210.3
IP:  2001:4ca0:4001:f21::3
```

# Teil 1: Apache2 auf pcsec2 installieren

## DNS setzen

Auf `pcsec2` wurde zuerst der DNS-Server gesetzt:

```bash
echo "nameserver 2001:4ca0::53:1" > /etc/resolv.conf
```

### Warum?

`apt` muss Domainnamen wie `archive.debian.org` auflösen können. Ohne funktionierendes DNS kann das System keine Pakete herunterladen.

### Erklärung

```bash
echo "nameserver 2001:4ca0::53:1"
```

Dieser Teil gibt die Zeile aus, die den DNS-Server definiert.

```bash
> /etc/resolv.conf
```

Das `>` schreibt diese Zeile in die Datei `/etc/resolv.conf`. Diese Datei wird vom System für DNS verwendet.

---

## Route zum DNS-Server setzen

```bash
ip -6 route replace 2001:4ca0::53:1/128 via 2001:db6::ff dev ens2
```

### Warum?

Der DNS-Server war zuerst nicht erreichbar. Deshalb wurde eine explizite Route gesetzt, damit Pakete zum DNS-Server über den funktionierenden Gateway `2001:db6::ff` und das Interface `ens2` laufen.

### Erklärung

```bash
ip
```

Das Linux-Netzwerktool für Adressen und Routen.

```bash
-6
```

Es geht um IPv6.

```bash
route replace
```

Die Route wird erstellt oder ersetzt, falls sie schon existiert.

```bash
2001:4ca0::53:1/128
```

Das Ziel ist genau diese eine IPv6-Adresse. `/128` bedeutet bei IPv6 eine einzelne Adresse.

```bash
via 2001:db6::ff
```

Der nächste Router ist `2001:db6::ff`.

```bash
dev ens2
```

Die Pakete werden über das Interface `ens2` geschickt.

---

## Default-Route setzen

```bash
ip -6 route replace default via 2001:db6::ff dev ens2 metric 100
```

### Warum?

Damit auch allgemeiner IPv6-Verkehr nach außen funktioniert, wurde die Default-Route auf den funktionierenden Gateway gesetzt.

### Erklärung

```bash
default
```

Diese Route wird verwendet, wenn es keine spezifischere Route gibt.

```bash
via 2001:db6::ff dev ens2
```

Verkehr wird über diesen Gateway und dieses Interface geschickt.

```bash
metric 100
```

Die Metrik bestimmt die Priorität der Route. Eine kleinere Metrik ist meistens bevorzugt.

# Teil 5: Zertifikatserweiterungen mit SAN erstellen

```bash
cat > apache2_ext.cnf <<EOF
[ server_cert ]
basicConstraints = CA:false
subjectKeyIdentifier = hash
authorityKeyIdentifier = keyid,issuer
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
subjectAltName = @alt_names

[ alt_names ]
DNS.1 = $HOST
IP.1 = $IP4
IP.2 = $IP6
EOF
```

## Warum?

Das Zertifikat braucht Subject Alternative Names, weil dort DNS-Name, IPv4 und IPv6 eingetragen werden.

## Erklärung der Einträge

```text
[ server_cert ]
```

Name der Extension-Sektion.

```text
basicConstraints = CA:false
```

Dieses Zertifikat ist kein CA-Zertifikat und darf keine anderen Zertifikate signieren.

```text
subjectKeyIdentifier = hash
```

Erstellt eine Kennung für den öffentlichen Schlüssel.

```text
authorityKeyIdentifier = keyid,issuer
```

Verweist auf die CA, die das Zertifikat ausgestellt hat.

```text
keyUsage = critical, digitalSignature, keyEncipherment
```

Legt fest, wofür der Schlüssel verwendet werden darf.

```text
extendedKeyUsage = serverAuth
```

Das Zertifikat darf für Server-Authentisierung genutzt werden. Das ist für HTTPS notwendig.

```text
subjectAltName = @alt_names
```

Verweist auf die SAN-Liste.

```text
DNS.1 = $HOST
IP.1 = $IP4
IP.2 = $IP6
```

Damit stehen Hostname, IPv4 und IPv6 im Zertifikat.

# Teil 6: Problem mit Seriennummer beheben

Beim ersten Signieren kam dieser Fehler:

```text
ERROR:Serial number 1000 has already been issued
```

## Warum?

OpenSSL nutzt eine Seriennummer für jedes Zertifikat. Die Datei `serial` enthielt noch:

```text
1000
```

Diese Seriennummer war aber bereits für das Zertifikat aus Aufgabe 11(c) verwendet worden. Auch ein widerrufenes Zertifikat behält seine Seriennummer. Eine CA darf dieselbe Seriennummer nicht erneut ausgeben.

## Prüfung

```bash
cat serial
cat index.txt
```

`cat serial` zeigt die nächste geplante Seriennummer.

`cat index.txt` zeigt die CA-Datenbank mit ausgestellten und widerrufenen Zertifikaten.

## Lösung

```bash
echo 1001 > serial
rm -f newcerts/apache2.pem
```

`echo 1001 > serial` setzt die nächste Seriennummer auf `1001`.

`rm -f newcerts/apache2.pem` entfernt eine eventuell kaputte oder unvollständige Zertifikatsdatei.

# Teil 7: Zertifikat mit der eigenen CA signieren

```bash
openssl ca \
  -config openssl.cnf \
  -extfile apache2_ext.cnf \
  -extensions server_cert \
  -days 365 \
  -notext \
  -batch \
  -in apache2.csr \
  -out newcerts/apache2.pem
```

## Erklärung

```bash
openssl ca
```

Verwendet die CA-Funktion von OpenSSL.

```bash
-config openssl.cnf
```

Lädt die CA-Konfiguration mit Pfaden zu CA-Zertifikat, CA-Schlüssel, Datenbank und Seriennummer.

```bash
-extfile apache2_ext.cnf
```

Lädt die zusätzliche Extension-Datei mit SANs.

```bash
-extensions server_cert
```

Verwendet die Sektion `[ server_cert ]`.

```bash
-days 365
```

Das Zertifikat ist 365 Tage gültig.

```bash
-notext
```

Schreibt keinen zusätzlichen Textblock in die Zertifikatsdatei.

```bash
-batch
```

Keine interaktiven Bestätigungsfragen.

```bash
-in apache2.csr
```

Der CSR, der signiert wird.

```bash
-out newcerts/apache2.pem
```

Das fertige Zertifikat wird in `newcerts/apache2.pem` gespeichert.

## Erfolgreiches Ergebnis

```text
Certificate is to be certified until May 18 10:13:31 2027 GMT (365 days)
Write out database with 1 new entries
Data Base Updated
```

Das bedeutet, dass das Zertifikat erfolgreich erstellt und die CA-Datenbank aktualisiert wurde.

# Teil 12: HTTPS-Site erstellen

```bash
cat > /etc/apache2/sites-available/secp-ssl.conf <<'EOF'
<VirtualHost *:443>
    ServerName gruppe09.secp.lab.nm.ifi.lmu.de
    DocumentRoot /var/www/html

    SSLEngine on
    SSLCertificateFile /etc/ssl/secp/apache2.pem
    SSLCertificateKeyFile /etc/ssl/secp/apache2.key
    SSLCertificateChainFile /etc/ssl/secp/cacert.pem

    ErrorLog ${APACHE_LOG_DIR}/secp_ssl_error.log
    CustomLog ${APACHE_LOG_DIR}/secp_ssl_access.log combined
</VirtualHost>
EOF
```

## Erklärung der Konfiguration

```apache
<VirtualHost *:443>
```

Apache lauscht auf Port `443` für HTTPS.

```apache
ServerName gruppe09.secp.lab.nm.ifi.lmu.de
```

Der Hostname des VirtualHosts. Er passt zum Zertifikat.

```apache
DocumentRoot /var/www/html
```

Apache liefert Inhalte aus `/var/www/html` aus.

```apache
SSLEngine on
```

Aktiviert TLS für diesen VirtualHost.

```apache
SSLCertificateFile /etc/ssl/secp/apache2.pem
```

Pfad zum Server-Zertifikat.

```apache
SSLCertificateKeyFile /etc/ssl/secp/apache2.key
```

Pfad zum privaten Server-Schlüssel.

```apache
SSLCertificateChainFile /etc/ssl/secp/cacert.pem
```

Pfad zum CA-Zertifikat. Dadurch kann Apache die Zertifikatskette mitsenden.

```apache
ErrorLog ...
CustomLog ...
```

Logdateien für Fehler und Zugriffe.

## Wieder auf pcsec2

```bash
chmod 600 /etc/ssl/secp/apache2.key
chmod 644 /etc/ssl/secp/apache2.pem
chmod 644 /etc/ssl/secp/cacert.pem
```

```bash
a2enmod ssl
```

```bash
cat > /etc/apache2/sites-available/secp-ssl.conf <<'EOF'
<VirtualHost *:443>
    ServerName gruppe09.secp.lab.nm.ifi.lmu.de
    DocumentRoot /var/www/html

    SSLEngine on
    SSLCertificateFile /etc/ssl/secp/apache2.pem
    SSLCertificateKeyFile /etc/ssl/secp/apache2.key
    SSLCertificateChainFile /etc/ssl/secp/cacert.pem

    ErrorLog ${APACHE_LOG_DIR}/secp_ssl_error.log
    CustomLog ${APACHE_LOG_DIR}/secp_ssl_access.log combined
</VirtualHost>
EOF
```

```bash
a2ensite secp-ssl.conf
apache2ctl configtest
service apache2 restart
```
