# Aufgabe 11(c): RSA-Key-Pair mit DES3 und signiertes Zertifikat
12345678
## Ziel der Aufgabe

In Aufgabe 11(c) sollte ein neues Public/Private RSA-Key-Pair mit folgenden Eigenschaften erstellt werden:

```text
Verschlüsselung des privaten Schlüssels: DES3
Schlüssellänge: 2048 Bit
Common Name: pcsec1.secp.lab.nm.ifi.lmu.de
Gültigkeit des Zertifikats: 1 Jahr
```

Der private Schlüssel musste unter folgendem Pfad gespeichert werden:

```bash
/home/secpgast/Abgaben/11/keys/11c.key
```

Das signierte Zertifikat musste unter folgendem Pfad gespeichert werden:

```bash
/home/secpgast/Abgaben/11/newcerts/11c.pem
```

Das Zertifikat sollte mit der eigenen CA aus Aufgabe 11(a) signiert werden.

---

## Warum machen wir das?

In Aufgabe 11(a) wurde eine eigene Certificate Authority, also CA, erstellt.

Diese CA besteht aus:

```text
CA-Zertifikat: /home/secpgast/Abgaben/11/cacert.pem
CA-Private-Key: /home/secpgast/Abgaben/11/private/cakey.pem
```

Die CA kann verwendet werden, um andere Zertifikate zu signieren.

In Aufgabe 11(c) wird nun ein neues Zertifikat für `pcsec1.secp.lab.nm.ifi.lmu.de` erstellt. Dafür braucht man:

```text
1. Einen privaten RSA-Schlüssel für pcsec1
2. Einen Certificate Signing Request, kurz CSR
3. Eine Signatur durch die eigene CA
4. Das finale Zertifikat
```

Der private Schlüssel bleibt geheim. Das Zertifikat darf öffentlich sein und kann später verwendet werden, um die Identität von `pcsec1.secp.lab.nm.ifi.lmu.de` nachzuweisen.

Zuerst wurde in das Aufgabenverzeichnis gewechselt:

```bash
cd /home/secpgast/Abgaben/11
```

Dieses Verzeichnis enthält bereits die CA-Dateien aus Aufgabe 11(a) und 11(b).

## Erweiterung der OpenSSL-Konfiguration

Für das Zertifikat aus Aufgabe 11(c) wurde eine neue Extension-Sektion in die Datei `openssl.cnf` eingefügt:

```bash
cat >> openssl.cnf <<'EOF'

[ usr_cert ]
basicConstraints = CA:false
subjectKeyIdentifier = hash
authorityKeyIdentifier = keyid,issuer
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth, clientAuth
EOF
```

---

## Warum wurde `[ usr_cert ]` hinzugefügt?

Das Zertifikat aus Aufgabe 11(c) ist kein CA-Zertifikat. Es soll also nicht selbst wieder andere Zertifikate signieren können.

Deshalb wurde die Extension-Sektion `[ usr_cert ]` hinzugefügt.

### `basicConstraints = CA:false`

Damit wird festgelegt, dass dieses Zertifikat keine CA ist.

Das ist wichtig, weil nur die CA aus Aufgabe 11(a) Zertifikate signieren soll.

### `subjectKeyIdentifier = hash`

Damit bekommt das Zertifikat eine eindeutige Kennung für seinen öffentlichen Schlüssel.

### `authorityKeyIdentifier = keyid,issuer`

Damit wird im Zertifikat referenziert, welche CA das Zertifikat ausgestellt hat.

In unserem Fall ist das die eigene CA:

```text
LMU IFI SecP Gruppe 09 CA
```

### `keyUsage = critical, digitalSignature, keyEncipherment`

Damit wird festgelegt, wofür der Schlüssel verwendet werden darf.

```text
digitalSignature: Der Schlüssel darf für digitale Signaturen verwendet werden.
keyEncipherment: Der Schlüssel darf zur Schlüsselverschlüsselung verwendet werden.
critical: Clients müssen diese Einschränkung beachten.
```

### `extendedKeyUsage = serverAuth, clientAuth`

Damit wird festgelegt, dass das Zertifikat grundsätzlich für Server- und Client-Authentisierung geeignet ist.

Für diese Aufgabe ist besonders `serverAuth` sinnvoll, weil der Common Name auf einen Hostnamen zeigt:

```text
pcsec1.secp.lab.nm.ifi.lmu.de
```

## Privaten RSA-Schlüssel mit DES3 erzeugen

Befehl:

```bash
openssl genrsa -des3 -out keys/11c.key 2048
```

---

## Erklärung des Befehls

### `openssl genrsa`

Dieser OpenSSL-Befehl erzeugt einen RSA-Private-Key.

Aus diesem privaten Schlüssel kann der passende öffentliche Schlüssel abgeleitet werden. Zusammen bilden sie das Public/Private-Key-Pair.

### `-des3`

Damit wird der private Schlüssel mit DES3 verschlüsselt.

Das bedeutet: Die Datei `keys/11c.key` ist nicht direkt lesbar, sondern durch ein Passwort geschützt.

### `-out keys/11c.key`

Damit wird der private Schlüssel genau unter dem von der Aufgabe geforderten Pfad gespeichert:

```bash
/home/secpgast/Abgaben/11/keys/11c.key
```

### `2048`

Das ist die Schlüssellänge in Bit.

Die Aufgabe verlangt ausdrücklich eine Schlüssellänge von 2048 Bit.

---

## Ergebnis beim Erzeugen des Schlüssels

Beim Ausführen des Befehls wurde ein RSA-Schlüssel erzeugt:

```text
Generating RSA private key, 2048 bit long modulus
e is 65537 (0x010001)
```

Danach wurde ein Passwort für den Schlüssel abgefragt.

Zwischendurch erschien folgende Meldung:

```text
You must type in 4 to 1023 characters
```

Das bedeutet, dass das eingegebene Passwort zu kurz war.

Danach wurde ein gültiges Passwort eingegeben und bestätigt. Der Schlüssel wurde erfolgreich erstellt.

## Dateirechte für den privaten Schlüssel setzen

Befehl:

```bash
chmod 600 keys/11c.key
```

---

## Warum wurde `chmod 600` verwendet?

Der private Schlüssel ist sensibel.

Mit `chmod 600` darf nur der Besitzer der Datei den Schlüssel lesen und schreiben.

Das bedeutet:

```text
Besitzer: lesen und schreiben
Gruppe: kein Zugriff
Andere Benutzer: kein Zugriff
```

Das ist sinnvoll, weil private Schlüssel nicht für andere Benutzer lesbar sein sollten.

## CSR für das neue Zertifikat erstellen

Befehl:

```bash
openssl req \
  -new \
  -key keys/11c.key \
  -out 11c.csr \
  -subj "/C=DE/ST=Bavaria/L=Munich/O=LMU IFI SecP Gruppe 09/CN=pcsec1.secp.lab.nm.ifi.lmu.de/emailAddress=mana.jaqoubi@campus.lmu.de"
```

---

## Erklärung des Befehls

### `openssl req`

Dieser Befehl wird verwendet, um einen Certificate Signing Request, kurz CSR, zu erstellen.

### `-new`

Damit wird ein neuer CSR erzeugt.

### `-key keys/11c.key`

Damit wird der zuvor erzeugte private Schlüssel verwendet.

Der CSR gehört also zu genau diesem Schlüssel.

### `-out 11c.csr`

Damit wird der CSR in der Datei `11c.csr` gespeichert.

Diese Datei ist nur eine Zwischendatei, die später von der CA signiert wird.

### `-subj "..."`

Damit werden die Zertifikatsinformationen direkt über die Kommandozeile gesetzt.

Verwendet wurden:

```text
C = DE
ST = Bavaria
L = Munich
O = LMU IFI SecP Gruppe 09
CN = pcsec1.secp.lab.nm.ifi.lmu.de
emailAddress = mana.jaqoubi@campus.lmu.de
```

Besonders wichtig ist der Common Name:

```text
CN = pcsec1.secp.lab.nm.ifi.lmu.de
```

Genau dieser Common Name wird in der Aufgabenstellung verlangt.

---

## Warum wurde ein CSR erstellt?

Die CA signiert nicht direkt einen privaten Schlüssel.

Der normale Ablauf ist:

```text
Private Key erzeugen
CSR aus Private Key erzeugen
CSR von CA signieren lassen
Zertifikat erhalten
```

Der CSR enthält die öffentlichen Informationen und wird mit dem privaten Schlüssel signiert. Die CA prüft und signiert anschließend diesen Antrag.

---

## CSR mit der eigenen CA signieren

Befehl:

```bash
openssl ca \
  -config openssl.cnf \
  -extensions usr_cert \
  -days 365 \
  -notext \
  -batch \
  -in 11c.csr \
  -out newcerts/11c.pem
```

---

## Erklärung des Befehls

### `openssl ca`

Dieser Befehl verwendet die konfigurierte CA, um einen CSR zu signieren und daraus ein Zertifikat zu erstellen.

### `-config openssl.cnf`

Damit wird die CA-Konfiguration verwendet.

Darin stehen unter anderem:

```text
Pfad zur CA-Datenbank
Pfad zur Seriennummer
Pfad zum CA-Zertifikat
Pfad zum CA-Private-Key
Policy-Regeln
```

### `-extensions usr_cert`

Damit wird die zuvor hinzugefügte Extension-Sektion `[ usr_cert ]` verwendet.

Dadurch wird das neue Zertifikat als normales Endnutzer- beziehungsweise Host-Zertifikat erstellt und nicht als CA-Zertifikat.

### `-days 365`

Damit wird das Zertifikat für 365 Tage gültig gemacht.

Das entspricht der Aufgabenanforderung:

```text
Das Zertifikat soll 1 Jahr gültig sein.
```

### `-notext`

Damit wird verhindert, dass eine lange menschenlesbare Zertifikatsbeschreibung zusätzlich in die Zertifikatsdatei geschrieben wird.

### `-batch`

Damit läuft der Signiervorgang ohne interaktive Bestätigungsfragen.

### `-in 11c.csr`

Das ist der CSR, der signiert werden soll.

### `-out newcerts/11c.pem`

Damit wird das fertige signierte Zertifikat unter dem geforderten Pfad gespeichert:

```bash
/home/secpgast/Abgaben/11/newcerts/11c.pem
```

## Zertifikatsdetails prüfen

Befehl:

```bash
openssl x509 -in newcerts/11c.pem -noout -subject -issuer -dates
```

---

## Erklärung des Befehls

### `openssl x509`

Dieser Befehl wird verwendet, um X.509-Zertifikate zu lesen und zu prüfen.

### `-in newcerts/11c.pem`

Damit wird das neu erstellte Zertifikat als Eingabe verwendet.

### `-noout`

Damit wird nicht das komplette Zertifikat ausgegeben.

### `-subject`

Damit wird angezeigt, für wen das Zertifikat ausgestellt wurde.

### `-issuer`

Damit wird angezeigt, welche CA das Zertifikat ausgestellt hat.

### `-dates`

Damit werden Beginn und Ende der Gültigkeit angezeigt.

---

## Zertifikat gegen die eigene CA verifizieren

Befehl:

```bash
openssl verify -CAfile cacert.pem newcerts/11c.pem
```

---

## Erklärung des Befehls

### `openssl verify`

Dieser Befehl prüft, ob ein Zertifikat von einer vertrauenswürdigen CA signiert wurde.

### `-CAfile cacert.pem`

Damit wird das eigene CA-Zertifikat als vertrauenswürdige CA angegeben.

### `newcerts/11c.pem`

Das ist das Zertifikat, das geprüft werden soll.

---

## Ergebnis der Verifikation

Ausgabe:

```text
newcerts/11c.pem: OK
```

---

## Erklärung des Ergebnisses

`OK` bedeutet, dass das Zertifikat erfolgreich gegen die eigene CA geprüft wurde.

Das heißt:

```text
Das Zertifikat wurde korrekt von cacert.pem signiert.
Die Signatur ist gültig.
Die Zertifikatskette ist für diese CA vertrauenswürdig.
```

Damit wurde bestätigt, dass das Zertifikat korrekt mit der eigenen CA erstellt wurde.
