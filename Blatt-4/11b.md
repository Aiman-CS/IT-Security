# Aufgabe 11(b): Certificate Signing Request und Fingerprints

## Ziel der Aufgabe

In Aufgabe 11(b) sollte ein neuer Certificate Signing Request, kurz CSR, für den bereits bestehenden CA-Schlüssel erstellt werden.

Der CSR musste unter folgendem Pfad gespeichert werden:

```bash
/home/secpgast/Abgaben/11/careq.csr
```

Zusätzlich sollten zwei Fingerprints dieses Antrags erzeugt und gespeichert werden:

```bash
/home/secpgast/Abgaben/11/private/cakey.md5
/home/secpgast/Abgaben/11/private/cakey.sha1
```

## Warum machen wir das?

In Aufgabe 11(a) wurde bereits eine eigene Certificate Authority, also CA, erstellt. Dazu gehören:

```bash
private/cakey.pem
cacert.pem
```

Der private Schlüssel `private/cakey.pem` gehört zur CA. Mit diesem Schlüssel kann die CA später Zertifikate ausstellen oder signieren.

In Aufgabe 11(b) wird nun kein komplett neuer Schlüssel erstellt. Stattdessen wird für den bereits existierenden CA-Schlüssel ein neuer Zertifikatsantrag erzeugt. Dieser Antrag heißt Certificate Signing Request, kurz CSR.

Ein CSR enthält die öffentlichen Informationen, die später in einem Zertifikat stehen sollen, zum Beispiel:

```text
Country Name
State or Province Name
Locality Name
Organization Name
Common Name
Email Address
```

Der CSR enthält nicht den privaten Schlüssel. Er enthält nur die öffentlichen Zertifikatsinformationen und wird mit dem privaten Schlüssel signiert, damit geprüft werden kann, dass der Antrag wirklich zu diesem Schlüssel gehört.

## Ausgangsverzeichnis

Wir arbeiten im Aufgabenverzeichnis:

```bash
cd /home/secpgast/Abgaben/11
```

Dieses Verzeichnis enthält nach Aufgabe 11(a) bereits folgende Dateien und Ordner:

```bash
ls
```

Ergebnis:

```text
cacert.pem  crlnumber  index.txt  keys  newcerts  openssl.cnf  private  serial
```

## Bedeutung der vorhandenen Dateien und Ordner

### `cacert.pem`

Das ist das selbstsignierte CA-Zertifikat aus Aufgabe 11(a).

### `private/cakey.pem`

Das ist der private Schlüssel der CA. Dieser Schlüssel ist besonders sensibel und wurde mit AES256 verschlüsselt.

### `openssl.cnf`

Das ist die OpenSSL-Konfigurationsdatei. Darin stehen unter anderem:

```text
Pfad zur CA
Pfad zum privaten CA-Schlüssel
Pfad zum CA-Zertifikat
Subject-Daten wie C, ST, L, O, CN und E-Mail
Regeln für Zertifikate und Requests
```

Diese Datei wird verwendet, damit OpenSSL automatisch die richtigen Informationen für den CSR übernimmt.

### `index.txt`

Das ist die Datenbankdatei der CA. OpenSSL nutzt sie später, um ausgestellte und widerrufene Zertifikate zu verwalten.

### `serial`

Diese Datei enthält die nächste Seriennummer, die OpenSSL für ein Zertifikat verwenden kann.

### `crlnumber`

Diese Datei enthält die Nummer für Certificate Revocation Lists, also Widerrufslisten.

### `keys`

Dieser Ordner ist für Schlüssel vorgesehen, die später in weiteren Teilaufgaben erstellt werden.

### `newcerts`

Dieser Ordner ist für neu ausgestellte Zertifikate vorgesehen.

### `private`

Dieser Ordner enthält private oder sensible Dateien der CA, zum Beispiel den CA-Schlüssel und die Fingerprint-Dateien aus dieser Aufgabe.

## CSR erstellen

Befehl:

```bash
openssl req \
  -config openssl.cnf \
  -new \
  -key private/cakey.pem \
  -out careq.csr
```

## Erklärung des Befehls

### `openssl req`

`openssl req` wird verwendet, um Zertifikatsanträge, also CSRs, zu erstellen, zu lesen oder zu prüfen.

### `-config openssl.cnf`

Damit wird OpenSSL gesagt, dass es die Konfiguration aus der Datei `openssl.cnf` verwenden soll.

Das ist wichtig, weil dort die benötigten CA- und Subject-Informationen hinterlegt sind, zum Beispiel:

```text
C  = DE
ST = Bavaria
L  = Munich
O  = LMU IFI SecP Gruppe 09
CN = LMU IFI SecP Gruppe 09 CA
emailAddress = mana.jaqoubi@campus.lmu.de
```

### `-new`

Damit wird ein neuer CSR erzeugt.

### `-key private/cakey.pem`

Damit wird der bereits vorhandene private CA-Schlüssel verwendet.

Das ist genau das, was die Aufgabe verlangt: Es soll ein neuer CSR für den bestehenden CA-Schlüssel erzeugt werden.

### `-out careq.csr`

Damit wird der CSR unter dem geforderten Namen gespeichert:

```bash
/home/secpgast/Abgaben/11/careq.csr
```

## Warum wurde der bestehende CA-Schlüssel verwendet?

Die Aufgabe sagt ausdrücklich, dass ein CSR für den bestehenden CA-Schlüssel erzeugt werden soll.

Deshalb wurde kein neuer RSA-Schlüssel erstellt. Stattdessen wurde `private/cakey.pem` verwendet, also der private CA-Schlüssel aus Aufgabe 11(a).

Dadurch gehört der neue CSR zur bereits vorhandenen CA.

## MD5-Fingerprint erzeugen

Befehl:

```bash
openssl req \
  -in careq.csr \
  -noout \
  -fingerprint \
  -md5 > private/cakey.md5
```

## Erklärung des Befehls

### `-in careq.csr`

Damit wird der zuvor erstellte CSR als Eingabedatei verwendet.

### `-noout`

Dadurch wird nicht der komplette CSR ausgegeben.

### `-fingerprint`

Damit wird ein Fingerprint des CSR erzeugt.

Ein Fingerprint ist ein Hash-Wert, mit dem man den CSR eindeutig wiedererkennen kann.

### `-md5`

Damit wird MD5 als Hash-Verfahren verwendet.

Die Aufgabe verlangt ausdrücklich einen MD5-Fingerprint.

### `> private/cakey.md5`

Damit wird die Ausgabe nicht im Terminal angezeigt, sondern in diese Datei geschrieben:

```bash
/home/secpgast/Abgaben/11/private/cakey.md5
```

## SHA1-Fingerprint erzeugen

Befehl:

```bash
openssl req \
  -in careq.csr \
  -noout \
  -fingerprint \
  -sha1 > private/cakey.sha1
```

## Erklärung des Befehls

Dieser Befehl funktioniert wie der MD5-Befehl, verwendet aber SHA1 als Hash-Verfahren.

### `-sha1`

Damit wird der SHA1-Fingerprint erzeugt.

Die Aufgabe verlangt ausdrücklich auch einen SHA1-Fingerprint.

### `> private/cakey.sha1`

Damit wird die Ausgabe in folgende Datei geschrieben:

```bash
/home/secpgast/Abgaben/11/private/cakey.sha1
```

## Ergebnisdateien prüfen

Um zu prüfen, ob die Dateien existieren, kann folgender Befehl verwendet werden:

```bash
ls -l careq.csr private/cakey.md5 private/cakey.sha1
```

Damit sollte man sehen, dass folgende Dateien erstellt wurden:

```text
careq.csr
private/cakey.md5
private/cakey.sha1
```

## CSR-Subject anzeigen

Befehl:

```bash
openssl req -in careq.csr -noout -subject
```

Ergebnis:

```text
subject=C = DE, ST = Bavaria, L = Munich, O = LMU IFI SecP Gruppe 09, CN = LMU IFI SecP Gruppe 09 CA, emailAddress = mana.jaqoubi@campus.lmu.de
```

## Erklärung des Ergebnisses

Das Ergebnis zeigt, dass der CSR die richtigen Informationen enthält:

```text
Country Name: DE
State or Province Name: Bavaria
Locality Name: Munich
Organization Name: LMU IFI SecP Gruppe 09
Common Name: LMU IFI SecP Gruppe 09 CA
Email Address: mana.jaqoubi@campus.lmu.de
```

Diese Werte stammen aus der OpenSSL-Konfiguration `openssl.cnf`.

Damit ist überprüfbar, dass der CSR für die richtige CA und die richtige Gruppe erstellt wurde.

## CSR überprüfen

Befehl:

```bash
openssl req -in careq.csr -noout -verify
```

Ergebnis:

```text
verify OK
```

## Erklärung des Ergebnisses

`verify OK` bedeutet, dass der CSR gültig ist.

Das heißt:

```text
Der CSR ist korrekt aufgebaut.
Die Signatur des CSR ist gültig.
Der CSR passt zu dem privaten Schlüssel, mit dem er erzeugt wurde.
```

Damit wurde bestätigt, dass der CSR erfolgreich und korrekt erstellt wurde.

## Warum wurden die Fingerprints gespeichert?

Die Aufgabe verlangt, dass sowohl der MD5-Fingerprint als auch der SHA1-Fingerprint des CSR gespeichert werden.

Fingerprints sind kurze Hash-Werte, die zur Identifikation und Kontrolle eines Zertifikatsantrags verwendet werden können.

Wenn sich der CSR auch nur minimal ändern würde, dann würden sich auch die Fingerprints ändern.

Deshalb kann man mit den Fingerprints prüfen, ob der CSR unverändert ist.
