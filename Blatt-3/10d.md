# Blatt 3, Aufgabe 10d: Dynamische Firewall testen

## Aufgabenstellung

Die dynamische Firewall aus Aufgabe 10c soll durch Testen der benötigten Dienste und mit Hilfe eines Portscanners überprüft werden.

## Testsystem

- **pcsec1** (10.153.210.2): Hier läuft die dynamische Firewall aus 10c
- **pcsec2** (10.153.210.3): Von hier wird getestet (Portscan, SSH-Test)

## 1. TCP-Portscan mit nmap

### Befehl (auf pcsec2)

```bash
nmap -sT -p 20,21,22,23,25 10.153.210.2
```

- `nmap` = Netzwerk-Scanner
- `-sT` = TCP Connect Scan (vollständiger TCP-Handshake)
- `-p 20,21,22,23,25` = Nur die Ports scannen, die in der Firewall konfiguriert sind (FTP Data, FTP Control, SSH, Telnet, SMTP)
- `10.153.210.2` = Ziel: pcsec1

### Ergebnis

```text
Nmap scan report for 10.153.210.2
Host is up (-0.099s latency).
PORT   STATE  SERVICE
20/tcp closed ftp-data
21/tcp closed ftp
22/tcp open   ssh
23/tcp closed telnet
25/tcp closed smtp
MAC Address: 52:54:00:E3:07:5D (QEMU virtual NIC)
```

### Bewertung

| Port | Dienst | Status | Erwartet? | Erklärung |
|---:|---|---|---|---|
| 20 | FTP Data | closed | Ja | Port ist in der Firewall erlaubt, aber kein FTP-Server läuft → `closed` |
| 21 | FTP Control | closed | Ja | Port erlaubt, aber kein FTP-Server läuft → `closed` |
| 22 | SSH | **open** | Ja | SSH-Server läuft und Firewall erlaubt den Zugriff |
| 23 | Telnet | closed | Ja | Telnet ist nur zwischen pcsec1 ↔ pcsec2 erlaubt. Auf pcsec1 läuft kein Telnet-Server → `closed` |
| 25 | SMTP | closed | Ja | Port erlaubt, aber kein SMTP-Server läuft → `closed` |

**Wichtig:** `closed` bedeutet **nicht**, dass die Firewall den Port blockiert. Es bedeutet, dass der Port erreichbar ist (die Firewall lässt das Paket durch), aber kein Dienst auf dem Port lauscht. Das System antwortet mit TCP RST. Wenn die Firewall den Port blockieren würde, stünde dort `filtered` (keine Antwort, Paket wird verworfen).

## 2. UDP-Portscan mit nmap

### Befehl (auf pcsec2)

```bash
nmap -sU -p 53,123 10.153.210.2
```

- `-sU` = UDP Scan
- `-p 53,123` = DNS (53) und NTP (123)

### Ergebnis

```text
Nmap scan report for 10.153.210.2
Host is up (0.0022s latency).
PORT    STATE  SERVICE
53/udp  closed domain
123/udp closed ntp
MAC Address: 52:54:00:E3:07:5D (QEMU virtual NIC)
```

### Bewertung

| Port | Dienst | Status | Erwartet? | Erklärung |
|---:|---|---|---|---|
| 53 | DNS | closed | Ja | Port erlaubt, aber kein DNS-Server läuft → `closed` |
| 123 | NTP | closed | Ja | Port erlaubt, aber kein NTP-Server läuft → `closed` |

Auch hier: `closed` = Firewall lässt durch, aber kein Dienst lauscht.

## 3. SSH-Test

### Befehl (auf pcsec1, ausgehend zu pcsec2)

```bash
ssh -o ConnectTimeout=3 -o StrictHostKeyChecking=no 10.153.210.3 echo "SSH OK"
```

- `-o ConnectTimeout=3` = Timeout nach 3 Sekunden
- `-o StrictHostKeyChecking=no` = Host-Key automatisch akzeptieren
- `10.153.210.3` = pcsec2

### Ergebnis

```text
Warning: Permanently added '10.153.210.3' (ECDSA) to the list of known hosts.
root@10.153.210.3's password:
```

Die SSH-Verbindung wird erfolgreich aufgebaut – der Passwort-Prompt erscheint. Das zeigt:

- Die OUTPUT-Regel für SSH (Port 22, NEW) auf pcsec1 funktioniert
- Die ESTABLISHED-Regel lässt die Antwortpakete durch
- Die Firewall blockiert SSH nicht

## 4. Logging prüfen

### Befehl (auf pcsec1)

```bash
grep -E "SSH-IN-NEW|SMTP-IN-NEW|DNS-IN-QUERY" /var/log/kern.log | tail -10
```

### Ergebnis

```text
May 11 12:29:36 pcsec1 kernel: SSH-IN-NEW: IN=ens7 SRC=10.153.210.3 DST=10.153.210.2 PROTO=TCP SPT=51656 DPT=22 SYN
May 11 12:29:36 pcsec1 kernel: SMTP-IN-NEW: IN=ens7 SRC=10.153.210.3 DST=10.153.210.2 PROTO=TCP SPT=44500 DPT=25 SYN
May 11 12:30:03 pcsec1 kernel: DNS-IN-QUERY: IN=ens7 SRC=10.153.210.3 DST=10.153.210.2 PROTO=UDP SPT=46811 DPT=53
```

### Bewertung

| Log-Prefix | Was wurde geloggt | Korrekt? |
|---|---|---|
| `SSH-IN-NEW` | Neuer SSH-Verbindungsaufbau von pcsec2 (nmap TCP Connect auf Port 22) | Ja |
| `SMTP-IN-NEW` | Neuer SMTP-Verbindungsaufbau von pcsec2 (nmap TCP Connect auf Port 25) | Ja |
| `DNS-IN-QUERY` | DNS-Abfrage von pcsec2 (nmap UDP auf Port 53) | Ja |

Das Logging funktioniert korrekt:
- SSH und SMTP werden nur beim Verbindungsaufbau geloggt (`ctstate NEW` matcht nur das erste Paket)
- DNS wird bei jeder neuen Abfrage geloggt
- FTP und NTP erscheinen **nicht** im Log, weil sie ohne Logging konfiguriert sind

## 5. Connection-Tracking-Tabelle nach den Tests

### Befehl (auf pcsec1)

```bash
cat /proc/net/nf_conntrack
```

### Ergebnis

```text
ipv4     2 tcp      6 105 TIME_WAIT src=10.153.210.2 dst=10.153.210.3 sport=53410 dport=22 src=10.153.210.3 dst=10.153.210.2 sport=22 dport=53410 [ASSURED] mark=0 zone=0 use=2
```

Das zeigt eine SSH-Verbindung im `TIME_WAIT`-Status (Verbindung wurde gerade beendet). Das Connection Tracking funktioniert und trackt die Verbindungen korrekt.

## Zusammenfassung

Die dynamische Firewall aus 10c funktioniert korrekt:

- **SSH** (TCP 22): open – einziger laufender Dienst
- **FTP, SMTP, Telnet**: closed – Firewall lässt durch, aber kein Dienst läuft
- **DNS, NTP**: closed (UDP) – Firewall lässt durch, aber kein Dienst läuft
- **Logging**: SSH, SMTP und DNS werden korrekt geloggt (nur Verbindungsaufbau)
- **FTP, NTP**: Kein Logging – wie konfiguriert
- **Connection Tracking**: Funktioniert (Verbindungen werden in der conntrack-Tabelle verfolgt)
