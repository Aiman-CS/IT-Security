In Aufgabe 15 soll eine IPsec-Kommunikation im Praktikumsnetz mitgeschnitten und entschlüsselt werden.

| Rolle | Rechner | Adresse aus dem Mitschnitt |

1. die verschlüsselte IPsec-Kommunikation mitzuschneiden,
2. das ESP-Paket zu entschlüsseln,
3. die entschlüsselte UDP-Nachricht zu finden,
4. das gefundene Passwort unter folgendem Pfad auf `gwsec` zu speichern:


## 1. Abgabeordner erstellen

## 2. IPsec-Verkehr mitschneiden

Die Aufgabenstellung sagt, dass die Kommunikation alle fünf Minuten stattfindet. Deshalb wurde etwas länger als fünf Minuten mitgeschnitten.

Auf `gwsec`:

```bash
timeout 420 tcpdump -i any -s0 -w /tmp/ipsec15.pcap 'proto 50 or udp port 4500'
```

### Erklärung des Befehls

```bash
timeout 420
```

führt den folgenden Befehl maximal 420 Sekunden lang aus. Das sind 7 Minuten.

```bash
tcpdump
```

schneidet Netzwerkverkehr mit.

```bash
-i any
```

zeichnet auf allen Interfaces mit.

```bash
-s0
```

speichert die vollständigen Pakete und schneidet sie nicht ab.

```bash
-w /tmp/ipsec15.pcap
```

speichert den Mitschnitt als PCAP-Datei unter `/tmp/ipsec15.pcap`.

```bash
'proto 50 or udp port 4500'
```

filtert auf ESP und NAT-Traversal-Verkehr.

ESP verwendet IP-Protokollnummer `50`. Bei normalem IPsec ohne NAT-T ist das der relevante Verkehr. UDP-Port `4500` wird bei IPsec NAT-Traversal verwendet.

## 3. Mitschnitt prüfen

Nach dem Mitschnitt wurde die PCAP-Datei geprüft:

```bash
tcpdump -r /tmp/ipsec15.pcap -nn
```

Ergebnis:

```text
reading from file /tmp/ipsec15.pcap, link-type LINUX_SLL (Linux cooked)
11:04:01.970005 IP6 2001:4ca0:4001:f00::1 > 2001:4ca0:4001:f00::21: ESP(spi=0x00001000,seq=0x166), length 68
```

### Bedeutung

Der Mitschnitt enthält ein ESP-Paket.

Wichtige Werte aus dem Paket:

| Feld | Wert |
|---|---:|
| Quelle | `2001:4ca0:4001:f00::1` |
| Ziel | `2001:4ca0:4001:f00::21` |
| Protokoll | ESP |
| SPI | `0x00001000` |
| Sequenznummer | `0x166`, dezimal `358` |
| ESP-Länge | `68` Bytes |

Der SPI, also Security Parameter Index, identifiziert die IPsec Security Association. Er sagt dem Empfänger, welche Schlüssel und Algorithmen für dieses Paket verwendet werden müssen.

## 4. Preshared-Key in Hex umwandeln

Der aus der Aufgabenstellung bekannte Schlüssel lautet:

```text
secpmachtspass!!
```

Für Tools wie Wireshark oder OpenSSL wird der Schlüssel oft in Hex-Form benötigt.

Befehl:

```bash
echo -n 'secpmachtspass!!' | xxd -p
```

Ergebnis:

```text
736563706d6163687473706173732121
```

### Erklärung

`echo -n` gibt den Text ohne Zeilenumbruch aus.

`xxd -p` wandelt die Bytes in eine reine Hex-Darstellung um.

Der Schlüssel hat 16 Zeichen und damit 16 Bytes. Das passt genau zu AES-128, da AES-128 einen Schlüssel mit 128 Bit verwendet.

```text
16 Bytes * 8 Bit = 128 Bit
```

## 6. Aufbau des ESP-Pakets

Das Paket aus dem Mitschnitt hat folgenden groben Aufbau:

```text
Linux cooked header
IPv6 header
ESP header
IV
verschlüsselte ESP-Nutzdaten
ICV
```

Für unsere Datei ist wichtig:

| Bestandteil | Länge | Bedeutung |
|---|---:|---|
| Linux cooked header | 16 Bytes | Header durch `tcpdump -i any` |
| IPv6 header | 40 Bytes | IPv6 Quelle, Ziel und Next Header ESP |
| ESP header | 8 Bytes | SPI und Sequenznummer |
| IV | 16 Bytes | Initialisierungsvektor für AES-CBC |
| Ciphertext | 32 Bytes | verschlüsselter UDP-Inhalt inklusive Padding |
| ICV | 12 Bytes | Integritätswert, nicht verschlüsselt |

Der Initialisierungsvektor aus dem Paket war:

```text
c0b4467a198de648d45983b64fc75252
```

Die ICV-Länge war in diesem Fall 12 Bytes. Dadurch bleibt für den eigentlichen AES-CBC-Ciphertext eine Länge von 32 Bytes. Das passt, weil AES-CBC blockweise mit 16-Byte-Blöcken arbeitet.

## 7. Entschlüsselung mit Python und OpenSSL

Das folgende Skript wurde auf `gwsec` erstellt:

```bash
cat > /tmp/decrypt_ipsec15.py <<'PY'
#!/usr/bin/env python3
import struct, subprocess, socket, re

PCAP = "/tmp/ipsec15.pcap"
KEY = "736563706d6163687473706173732121"

def ip6(b):
    return socket.inet_ntop(socket.AF_INET6, b)

with open(PCAP, "rb") as f:
    f.read(24)

    while True:
        hdr = f.read(16)
        if len(hdr) < 16:
            break

        _, _, incl_len, _ = struct.unpack("<IIII", hdr)
        pkt = f.read(incl_len)

        ip = pkt[16:]

        if len(ip) < 40 or ip[0] >> 4 != 6 or ip[6] != 50:
            continue

        src = ip6(ip[8:24])
        dst = ip6(ip[24:40])
        esp = ip[40:]

        spi, seq = struct.unpack("!II", esp[:8])
        iv = esp[8:24]

        print("SRC:", src)
        print("DST:", dst)
        print("SPI:", hex(spi))
        print("SEQ:", seq)
        print("IV:", iv.hex())

        for icv_len in [0, 12, 16]:
            ct = esp[24:-icv_len] if icv_len else esp[24:]

            if len(ct) % 16 != 0:
                continue

            out = subprocess.run(
                ["openssl", "enc", "-d", "-aes-128-cbc", "-K", KEY, "-iv", iv.hex(), "-nopad"],
                input=ct,
                stdout=subprocess.PIPE,
                stderr=subprocess.PIPE
            ).stdout

            print("\n=== ICV LEN", icv_len, "===")
            print(out)
            print(out.decode("latin1", errors="ignore"))

            readable = re.findall(rb"[A-Za-z0-9_!?.:-]{4,}", out)
            print("READABLE:", [x.decode("latin1") for x in readable])
PY
```

Danach wurde es ausgeführt:

```bash
python3 /tmp/decrypt_ipsec15.py
```

Ausgabe:

```text
SRC: 2001:4ca0:4001:f00::1
DST: 2001:4ca0:4001:f00::21
SPI: 0x1000
SEQ: 358
IV: c0b4467a198de648d45983b64fc75252

=== ICV LEN 12 ===
b'\xceN\x04\xd2\x00\x1c\x87}Gut gemacht 15062020\x01\x02\x02\x11'
Gut gemacht 15062020
READABLE: ['gemacht', '15062020']
```

## 8. Erklärung des entschlüsselten Plaintexts

Die entschlüsselten Bytes waren:

```text
ce 4e 04 d2 00 1c 87 7d 47 75 74 20 67 65 6d 61 63 68 74 20 31 35 30 36 32 30 32 30 01 02 02 11
```

Diese Bytes lassen sich so zerlegen:

| Bytes | Bedeutung |
|---|---|
| `ce 4e` | UDP Source Port |
| `04 d2` | UDP Destination Port |
| `00 1c` | UDP Length |
| `87 7d` | UDP Checksum |
| `47 75 74 20 67 65 6d 61 63 68 74 20 31 35 30 36 32 30 32 30` | UDP-Nutzdaten |
| `01 02` | ESP Padding |
| `02` | Pad Length |
| `11` | Next Header, UDP |

### UDP Header

Der Destination Port ist:

```text
04 d2 = 1234
```

Das bestätigt, dass die entschlüsselte Nachricht wirklich die gesuchte UDP-Kommunikation auf Port `1234` ist.

Die UDP Length ist:

```text
00 1c = 28
```

Das bedeutet:

```text
8 Bytes UDP Header + 20 Bytes Nutzdaten = 28 Bytes
```

### UDP-Nutzdaten

Die Nutzdaten ergeben als ASCII-Text:

```text
Gut gemacht 15062020
```

Der passwortartige Teil der Nachricht ist:

```text
15062020
```

Falls das Testsystem die vollständige entschlüsselte Nachricht erwartet, wäre die vollständige Nutzlast:

```text

```

Da die Aufgabenstellung ausdrücklich vom Passwort spricht, ist `15062020` der naheliegende Wert für `passwort.txt`.

# Teil 2, Theorieaufgabe

## Aufgabenfrage

Die Theoriefrage lautet sinngemäß:

Welche Sicherheitsmechanismen haben VPN-Tunnel üblicherweise, um solche Angriffe zu verhindern? Außerdem soll die hier benutzte Konfiguration mit den Konfigurationen aus Aufgabe 13 und 14 verglichen werden.

---

## 1. Warum war der Angriff hier möglich?

Der Angriff war hier möglich, weil der symmetrische Schlüssel für die Datenentschlüsselung direkt bekannt war.

Die Aufgabenstellung nennt den AES128/Rijndael Preshared-Key:

```text
secpmachtspass!!
```

Dadurch musste der Angreifer AES nicht brechen. Es reichte aus:

1. das ESP-Paket mitzuschneiden,
2. SPI, IV und Ciphertext aus dem Paket zu extrahieren,
3. den bekannten AES-128-Key in Hex umzuwandeln,
4. den Ciphertext mit AES-128-CBC zu entschlüsseln,
5. den UDP-Plaintext auszulesen.

Wichtig ist: Nicht AES selbst war hier schwach. Schwach war die Konfiguration beziehungsweise die Tatsache, dass der Schlüssel bekannt war und direkt zur Entschlüsselung verwendet werden konnte.

---

## 2. Welche Schutzmechanismen haben VPNs normalerweise?

### Mechanismus 1: Sichere Schlüsselaushandlung

Moderne VPNs verwenden normalerweise nicht einfach einen festen, öffentlich bekannten Schlüssel zur Datenverschlüsselung.

Stattdessen werden Sitzungsschlüssel dynamisch ausgehandelt.

Bei IPsec passiert das typischerweise über IKE oder IKEv2.

Dabei werden aus einem gemeinsamen Geheimnis, Zertifikaten und einem Diffie-Hellman-Schlüsselaustausch frische Schlüssel für die eigentliche ESP-Verschlüsselung abgeleitet.

### Mechanismus 2: Diffie-Hellman und Perfect Forward Secrecy

Durch Diffie-Hellman können zwei Endpunkte einen gemeinsamen Sitzungsschlüssel erzeugen, ohne den eigentlichen Schlüssel über das Netz zu übertragen.

Perfect Forward Secrecy bedeutet:

Wenn später ein langfristiger Schlüssel bekannt wird, sollen alte Mitschnitte trotzdem nicht nachträglich entschlüsselt werden können.

Das schützt genau gegen das Szenario, dass jemand Traffic mitschneidet und später an einen Schlüssel kommt.

### Mechanismus 3: Gegenseitige Authentifizierung

VPN-Endpunkte authentifizieren sich normalerweise gegenseitig.

Das kann passieren durch:

- Pre-Shared Keys,
- Zertifikate,
- Signaturen,
- Benutzerkonten,
- zusätzliche Faktoren.

Dadurch soll verhindert werden, dass ein Angreifer sich als VPN-Gegenstelle ausgibt.

### Mechanismus 4: Integritätsschutz

VPNs schützen nicht nur gegen Mitlesen, sondern auch gegen Manipulation.

Dafür werden zum Beispiel HMAC-Verfahren oder AEAD-Verfahren verwendet.

Beispiele:

```text
HMAC-SHA256
AES-GCM
ChaCha20-Poly1305
```

Bei IPsec wird dafür häufig ESP-Authentication oder ein AEAD-Modus genutzt.

### Mechanismus 5: Anti-Replay-Schutz

ESP-Pakete enthalten Sequenznummern.

Der Empfänger kann dadurch erkennen, ob ein altes Paket erneut gesendet wurde.

Das verhindert Replay-Angriffe, bei denen ein Angreifer alte verschlüsselte Pakete einfach noch einmal ins Netz einspielt.

### Mechanismus 6: Rekeying und begrenzte Lebensdauer von Schlüsseln

VPNs verwenden Sitzungsschlüssel normalerweise nur begrenzt lange.

Nach einer bestimmten Zeit oder Datenmenge werden neue Schlüssel ausgehandelt.

Das reduziert den Schaden, falls ein Sitzungsschlüssel kompromittiert wird.

### Mechanismus 7: Tunnel-Modus und Traffic Selectors

Bei IPsec kann zwischen Transport-Modus und Tunnel-Modus unterschieden werden.

Im Transport-Modus bleibt der äußere IP-Header sichtbar. Nur die Nutzdaten des IP-Pakets werden geschützt.

Im Tunnel-Modus wird ein komplettes inneres IP-Paket geschützt und in ein äußeres IP-Paket eingepackt.

Das ist besonders wichtig für Site-to-Site-VPNs, weil dabei ganze Subnetze über ein Gateway geschützt werden können.

```bash
swanctl --list-sas
```

### Rolle von Policies und States

```bash
ip xfrm policy
```

zeigt, welcher Verkehr durch IPsec geschützt werden soll.

Beispielhaft bedeutet eine Policy:

```text
Traffic von A nach B muss durch ESP geschützt werden.
```

```bash
ip xfrm state
```

zeigt die konkreten Security Associations.

Dort stehen unter anderem:

- SPI,
- Quelle und Ziel,
- Verschlüsselungsalgorithmus,
- Schlüsselmaterial,
- Authentifizierungsalgorithmus.

Damit trennt IPsec sauber zwischen:

1. der Entscheidung, welcher Verkehr geschützt werden muss,
2. der konkreten kryptografischen Umsetzung dieses Schutzes.

## Aufgabe 13(b), OpenVPN

In Aufgabe 13(b) wurde IPsec deaktiviert und ein OpenVPN-Tunnel eingerichtet.

OpenVPN arbeitet anders als IPsec.

OpenVPN läuft im User-Space und erstellt ein virtuelles Interface, zum Beispiel `tun0`.

Die Daten werden dann über dieses Interface geschickt und von OpenVPN über UDP oder TCP verschlüsselt transportiert.

Typische Merkmale aus der Umsetzung:

- eigenes virtuelles Interface,
- Tunneladressen wie `10.1.0.1` und `10.1.0.2`,
- Start über `systemctl start openvpn@secp`,
- Transport über einen normalen UDP-Port,
- einfacheres Debugging über `systemctl`, `journalctl`, `ip addr` und `tcpdump`.

Wenn OpenVPN mit einem statischen Schlüssel betrieben wird, muss dieser Schlüssel ebenfalls geheim bleiben. Trotzdem ist der Angriff aus Aufgabe 15 nicht direkt vergleichbar, weil dort der konkrete ESP-Datenschlüssel aus der Aufgabenstellung bekannt war.

In produktiven OpenVPN-Setups verwendet man außerdem meistens Zertifikate und TLS, nicht nur einen einfachen statischen Schlüssel.

## Warum ist Aufgabe 14 sicherer als Aufgabe 15?

Aufgabe 14 nutzt Zertifikatsauthentifizierung statt eines direkt bekannten Datengrundschlüssels.

Das bedeutet:

- die Gegenstelle wird über Zertifikate authentifiziert,
- der private Schlüssel wird nicht über das Netz übertragen,
- IKE beziehungsweise ISAKMP handelt Sitzungsschlüssel aus,
- Diffie-Hellman wird verwendet,
- PFS ist aktiviert,
- ESP nutzt Integritätsschutz mit HMAC-SHA256,
- die Schlüssel haben eine begrenzte Lebensdauer.

Ein passiver Angreifer, der nur den Traffic mitschneidet, kann damit die Pakete nicht einfach entschlüsseln.

Der Angreifer bräuchte zusätzlich Zugriff auf das relevante Schlüsselmaterial und müsste je nach Konfiguration auch die Sitzungsschlüssel rekonstruieren können.

Das ist genau der Unterschied zu Aufgabe 15: Dort war der relevante AES-Schlüssel bekannt und reichte zur Entschlüsselung des mitgeschnittenen Pakets aus.

# 6. Warum verhindert Aufgabe 14 genau diesen Angriff?

Der Angriff aus Aufgabe 15 funktioniert nur, weil der Angreifer das passende Schlüsselmaterial besitzt.

In einer normalen IPsec-Konfiguration wie in Aufgabe 14 reicht ein Mitschnitt alleine nicht aus.

Grund:

1. Die Endpunkte authentifizieren sich mit Zertifikaten.
2. Sitzungsschlüssel werden dynamisch ausgehandelt.
3. PFS sorgt dafür, dass alte Sitzungen nicht einfach durch spätere Schlüsselkompromittierung entschlüsselt werden können.
4. HMAC-SHA256 schützt die Pakete gegen Manipulation.
5. Rekeying begrenzt die Lebensdauer der Schlüssel.
6. Anti-Replay-Schutz verhindert das Wiederverwenden alter Pakete.

Deshalb kann ein Angreifer nicht einfach:

```text
Paket mitschneiden + bekannten Key einsetzen + Plaintext lesen
```

sondern müsste die eigentliche VPN-Sicherheit brechen oder an internes Schlüsselmaterial gelangen.

# 7. Kurze Theorieantwort für die Abgabe

```text
VPN-Tunnel verhindern solche Angriffe normalerweise durch eine Kombination aus sicherer Schlüsselaushandlung, gegenseitiger Authentifizierung, Integritätsschutz, Anti-Replay-Schutz, Rekeying und Perfect Forward Secrecy. Bei IPsec werden die eigentlichen ESP-Sitzungsschlüssel üblicherweise über IKE beziehungsweise ISAKMP ausgehandelt. Der langfristige Schlüssel oder das Zertifikat wird dabei nicht einfach als direkter Datengrundschlüssel für alle Pakete benutzt. Durch Diffie-Hellman und PFS kann ein später bekannt gewordener langfristiger Schlüssel alte Mitschnitte nicht automatisch entschlüsselbar machen. Zusätzlich schützen HMAC oder AEAD-Verfahren die Pakete gegen Manipulation und Sequenznummern verhindern Replay-Angriffe.

Die in Aufgabe 15 verwendete Konfiguration ist absichtlich schwach, weil der AES128/Rijndael-Schlüssel aus der Aufgabenstellung bekannt ist. Dadurch reicht ein passiver Mitschnitt des ESP-Pakets aus, um mit SPI, IV und dem bekannten Key den AES-CBC-Ciphertext zu entschlüsseln. Der Angriff bricht also nicht AES selbst, sondern nutzt die unsichere Schlüsselverfügbarkeit aus.

In Aufgabe 13 wurde IPsec mit strongSwan beziehungsweise OpenVPN eingerichtet. Beim IPsec-Teil dient der PSK zur IKE-Authentifizierung und Schlüsselaushandlung, während die eigentlichen ESP Security Associations daraus abgeleitet werden. Bei OpenVPN wird der Verkehr über ein eigenes Tunnelinterface geschützt und über UDP oder TCP transportiert. Beide Varianten sind sicherer als Aufgabe 15, solange die verwendeten Schlüssel geheim bleiben und sauber ausgehandelt werden.

Aufgabe 14 ist noch stärker, weil dort ein IPv6-IPsec-Tunnel mit Zertifikatsauthentifizierung verwendet wird. Die Konfiguration nutzt AES, SHA256, RSA-Signaturen, HMAC-SHA256, eine PFS-Gruppe und eine begrenzte Lifetime. Dadurch schützt sie besser gegen passives Mitschneiden, nachträgliche Entschlüsselung und Manipulation als die vereinfachte Konfiguration aus Aufgabe 15.
```
