# Übungsblatt 06, Aufgabe 16(c)

# Delegation der Subzone mit Glue Records

## Kontext der Aufgabe

In Aufgabe 16(c) soll die Zone `sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de` im Zonendatei der Parent-Zone auf dem Server `dns` delegiert werden.

Die Parent-Zone ist:

```text
 gruppe09.secp-int.lab.nm.ifi.lmu.de
```

Die Subzone ist:

```text
 sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de
```

Für die Subzone sollen zwei Nameserver eingetragen werden:

```text
pcsec1.sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de
 dns.sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de
```

Dabei ist `pcsec1` der Master der Subzone und `dns` der Slave der Subzone.

Da beide Nameservernamen innerhalb der delegierten Subzone liegen, müssen in der Parent-Zone zusätzlich Glue Records eingetragen werden.

# 2. Warum Delegation notwendig ist

Die Parent-Zone `gruppe09.secp-int.lab.nm.ifi.lmu.de` kennt zunächst nur ihre eigenen Hosts, zum Beispiel:

```text
secserver.gruppe09.secp-int.lab.nm.ifi.lmu.de
 dns.gruppe09.secp-int.lab.nm.ifi.lmu.de
 findmegw.gruppe09.secp-int.lab.nm.ifi.lmu.de
```

Die Subzone `sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de` wird jedoch von anderen Nameservern verwaltet.

Damit ein Resolver weiß, wohin er Anfragen für `sub09` schicken muss, enthält die Parent-Zone NS Records für die Subzone.

Diese NS Records zeigen auf:

```text
pcsec1.sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de
 dns.sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de
```

Da diese Namen selbst innerhalb der Subzone liegen, braucht die Parent-Zone zusätzlich Glue Records. Glue Records sind A und AAAA Records für die Nameserver der delegierten Zone.

Ohne Glue Records könnte ein Resolver in eine Abhängigkeit geraten:

```text
Um sub09 aufzulösen, brauche ich den Nameserver von sub09.
Aber um den Nameservernamen von sub09 aufzulösen, müsste ich schon sub09 fragen.
```

Glue Records lösen dieses Problem, indem die Parent-Zone die IP-Adressen der zuständigen Nameserver direkt mitliefert.

# 4. Erklärung der Delegation

Die eigentliche Delegation besteht aus diesen beiden Records:

```dns
sub09       IN  NS      pcsec1.sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de.
sub09       IN  NS      dns.sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de.
```

Damit sagt die Parent-Zone:

```text
Für die Zone sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de sind diese beiden Nameserver zuständig.
```

`pcsec1` ist der Master der Subzone.

`dns` ist der Slave der Subzone.

Dadurch ist die Delegation redundant, weil zwei Nameserver für die Subzone angegeben sind.

---

# 5. Erklärung der Glue Records

Die Glue Records sind diese Einträge:

```dns
pcsec1.sub09    IN  A       10.153.210.2
pcsec1.sub09    IN  AAAA    2001:4ca0:4001:f21::2

dns.sub09       IN  A       10.153.210.251
dns.sub09       IN  AAAA    2001:4ca0:4001:f00::251
```

Sie liefern die IP-Adressen der Nameserver direkt in der Parent-Zone mit.

Das ist notwendig, weil die Nameservernamen innerhalb der Subzone liegen, die gerade erst delegiert wird.

Die vollständigen Namen lauten dadurch:

```text
pcsec1.sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de
 dns.sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de
```

# 8. Lokale Tests auf `dns`

Die Delegation wurde zuerst lokal auf `dns` getestet.


```text

```

Damit ist bestätigt, dass die Subzone an beide Nameserver delegiert ist.

Danach wurden die Glue Records getestet.

```bash
dig @127.0.0.1 pcsec1.sub09.gruppe09.secp-int.lab.nm.ifi.lmu.de A +short
```

```text

2001:4ca0:4001:f21::2
```

Ausgabe:

Damit sind sowohl die Delegation als auch die Glue Records korrekt eingerichtet.

# 10. Problem mit dem Testsystem

Das Testsystem fragte nicht direkt den Server `dns` unter `10.153.210.251` ab, sondern den Gruppeneinstieg:

```text
gruppe09.secp.lab.nm.ifi.lmu.de
```

Diese Adresse zeigte auf `gwsec` beziehungsweise auf eine Gateway-Adresse. Dadurch kam es zu einem Timeout, obwohl `dns` selbst korrekt antwortete.

Deshalb wurde auf `gwsec` Port 53 an `dns` weitergeleitet.

# 11. DNS-Forwarding auf `gwsec`

Auf `gwsec` wurde IPv4 Forwarding aktiviert:

```bash
echo 1 > /proc/sys/net/ipv4/ip_forward
```

Firewall-Regeln wurden geleert und auf Accept gesetzt:

```bash
iptables -F
iptables -t nat -F
iptables -t mangle -F

iptables -P INPUT ACCEPT
iptables -P OUTPUT ACCEPT
iptables -P FORWARD ACCEPT
```

Die Interfaces wurden aktiviert und die IP-Adressen gesetzt:

```bash
ip link set ens7 up
ip link set ens8 up

ip addr add 10.153.210.1/29 dev ens7 2>/dev/null || true
ip addr add 10.153.210.193/26 dev ens8 2>/dev/null || true
```

Dann wurden DNS-Anfragen an `dns` weitergeleitet:

```bash
iptables -t nat -A PREROUTING -p udp --dport 53 -j DNAT --to-destination 10.153.210.251:53
iptables -t nat -A PREROUTING -p tcp --dport 53 -j DNAT --to-destination 10.153.210.251:53

iptables -t nat -A POSTROUTING -d 10.153.210.251 -p udp --dport 53 -j MASQUERADE
iptables -t nat -A POSTROUTING -d 10.153.210.251 -p tcp --dport 53 -j MASQUERADE
```

Zusätzlich wurden für lokale Tests auf `gwsec` OUTPUT-DNAT-Regeln gesetzt:

```bash
iptables -t nat -A OUTPUT -d 10.153.210.193 -p udp --dport 53 -j DNAT --to-destination 10.153.210.251:53
iptables -t nat -A OUTPUT -d 10.153.210.193 -p tcp --dport 53 -j DNAT --to-destination 10.153.210.251:53
```

Diese Regeln sorgen dafür, dass DNS-Anfragen an `10.153.210.193` auf den echten DNS-Server `10.153.210.251` umgeleitet werden.
