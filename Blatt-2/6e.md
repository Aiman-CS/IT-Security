# Aufgabe 6e: IPv6-Rechner im Segment finden

## Befehle

```bash
ip -6 addr
ping6 -c 3 -I ens8 ff02::1
ip -6 neigh show dev ens8
ip -6 neigh show dev ens8 | grep -E "REACHABLE|STALE|DELAY|PROBE"
```

---

## Zusammenfassung

In Aufgabe **6e** geht es darum, warum ein Brute-Force-Scan des IPv6-Netzes

```text
2001:4ca0:4001:f00::/64
```

nicht praktikabel ist.

Ein `/64`-IPv6-Netz enthält:

```text
2^64 Adressen
```

Das sind:

```text
18.446.744.073.709.551.616 mögliche Adressen
```

Ein vollständiger Brute-Force-Scan würde also bedeuten, dass man über 18 Trillionen IPv6-Adressen durchprobieren müsste. Das ist praktisch nicht machbar.

Statt alle Adressen einzeln zu scannen, kann man vom Router aus IPv6-Multicast verwenden. Dafür wird die All-Nodes-Multicast-Adresse verwendet:

```text
ff02::1
```

Diese Adresse spricht alle IPv6-Knoten im lokalen Segment an. Hosts, die auf ICMPv6 Echo Requests reagieren, antworten darauf.

Auf `gwsec` ist das richtige Interface:

```text
ens8
```

Das sieht man an dieser Adresse:

```text
inet6 2001:4ca0:4001:f00::21/64 scope global
```

Damit liegt `ens8` im gesuchten Netz:

```text
2001:4ca0:4001:f00::/64
```

---

## Kurze Antwort für die Abgabe

```text
Ein Brute-Force-Scan von 2001:4ca0:4001:f00::/64 ist nicht praktikabel, weil ein /64-IPv6-Netz 2^64 mögliche Adressen enthält. Das entspricht 18.446.744.073.709.551.616 Adressen. Ein vollständiges Durchprobieren aller Adressen würde daher extrem lange dauern und ist praktisch nicht durchführbar.

Stattdessen wurde vom Router gwsec aus IPv6-Multicast verwendet. Das passende Interface ist ens8, da es die Adresse 2001:4ca0:4001:f00::21/64 besitzt. Mit ping6 -c 3 -I ens8 ff02::1 wurde ein ICMPv6 Echo Request an die All-Nodes-Multicast-Adresse gesendet. Dadurch antworteten mehrere IPv6-Rechner im lokalen Segment. Anschließend wurden die gefundenen Nachbarn mit ip -6 neigh show dev ens8 angezeigt.
```

---

# Detaillierte Erklärung

## 1. Warum ist Brute-Force bei IPv6 /64 nicht praktikabel?

Das zu untersuchende Netz lautet:

```text
2001:4ca0:4001:f00::/64
```

Bei IPv6 bedeutet `/64`, dass die ersten 64 Bit der Adresse das Netz beschreiben. Die restlichen 64 Bit sind für Host-Adressen verfügbar.

Damit gibt es in diesem Segment:

```text
2^64 mögliche Host-Adressen
```

Das sind:

```text
18.446.744.073.709.551.616 Adressen
```

Bei IPv4 ist ein typisches `/24`-Netz sehr klein:

```text
2^8 = 256 Adressen
```

Ein IPv6-`/64` ist dagegen extrem groß. Ein vollständiger Scan würde daher viel zu lange dauern.

Deshalb ist ein Brute-Force-Scan wie dieser nicht sinnvoll:

```bash
nmap -6 -sn 2001:4ca0:4001:f00::/64
```

Nmap müsste theoretisch jede mögliche Adresse in diesem riesigen Bereich testen.

---

## 2. Richtigen Router-Interface bestimmen

Zuerst wurde auf `gwsec` die IPv6-Konfiguration angezeigt:

```bash
ip -6 addr
```

Relevanter Teil der Ausgabe:

```text
4: ens8: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP qlen 1000
    inet6 2001:4ca0:4001:f00::21/64 scope global
    inet6 fe80::5054:ff:fe84:904/64 scope link
```

Das zeigt:

- Das Interface heißt `ens8`.
- Es liegt im Netz `2001:4ca0:4001:f00::/64`.
- Die globale IPv6-Adresse von `gwsec` auf diesem Interface ist `2001:4ca0:4001:f00::21`.
- Die Link-Local-Adresse von `gwsec` auf diesem Interface ist `fe80::5054:ff:fe84:904`.

Damit ist `ens8` das richtige Interface für den Multicast-Ping.

---

## 3. IPv6-Multicast-Ping ausführen

Der Befehl war:

```bash
ping6 -c 3 -I ens8 ff02::1
```

Bedeutung:

- `ping6`: ICMPv6 Echo Request senden
- `-c 3`: nur 3 Pakete senden
- `-I ens8`: über das Interface `ens8` senden
- `ff02::1`: All-Nodes-Multicast-Adresse

Die Adresse `ff02::1` bedeutet:

```text
alle IPv6-Knoten im lokalen Segment
```

Deshalb antworten mehrere Hosts auf denselben Ping. In der Ausgabe sieht man deshalb `DUP!`, weil mehrere Antworten auf eine ICMP-Sequenz zurückkommen.

---

## 4. Ergebnis des Multicast-Pings

Ausgabe:

```text
PING ff02::1(ff02::1) from fe80::5054:ff:fe84:904%ens8 ens8: 56 data bytes
64 bytes from fe80::5054:ff:fe84:904%ens8: icmp_seq=1 ttl=64 time=0.040 ms
64 bytes from fe80::c62:7eff:fe66:9930%ens8: icmp_seq=1 ttl=64 time=2.90 ms (DUP!)
64 bytes from fe80::5054:ff:feb0:6296%ens8: icmp_seq=1 ttl=64 time=2.91 ms (DUP!)
64 bytes from fe80::5054:ff:fe3a:5632%ens8: icmp_seq=1 ttl=64 time=4.02 ms (DUP!)
```

Damit haben diese IPv6-Knoten auf ICMPv6 Echo Request reagiert:

```text
fe80::5054:ff:fe84:904
fe80::c62:7eff:fe66:9930
fe80::5054:ff:feb0:6296
fe80::5054:ff:fe3a:5632
```

Dabei ist:

```text
fe80::5054:ff:fe84:904
```

die eigene Link-Local-Adresse von `gwsec` auf `ens8`.

Die Statistik zeigt:

```text
3 packets transmitted, 3 received, +6 duplicates, 0% packet loss
```

Das bedeutet:

- Es wurden 3 Echo Requests gesendet.
- Der eigene Host hat 3 Antworten erhalten.
- Zusätzlich kamen 6 Duplikat-Antworten von anderen Hosts.
- Es gab keinen Paketverlust.
- Die Duplikate entstehen, weil mehrere Hosts auf die Multicast-Adresse antworten.

---

## 5. IPv6-Nachbartabelle anzeigen

Danach wurde die Neighbor-Tabelle angezeigt:

```bash
ip -6 neigh show dev ens8
```

Ausgabe:

```text
2001:4ca0:4001:f7f::1  FAILED
fe80::5054:ff:feb0:6296 lladdr 52:54:00:b0:62:96 router STALE
2001:4ca0:4001:f00::ff lladdr 52:54:00:b0:62:96 router STALE
2001:4ca0:4001:f00::1 lladdr fe:54:00:3a:56:32 router STALE
fe80::c62:7eff:fe66:9930 lladdr fe:54:00:3a:56:32 router STALE
fe80::5054:ff:fe3a:5632 lladdr 52:54:00:3a:56:32 STALE
```

Die Zeile:

```text
2001:4ca0:4001:f7f::1  FAILED
```

wird nicht als gefundener Host im gesuchten Segment gezählt, weil der Status `FAILED` ist und die Adresse außerdem nicht im Segment `2001:4ca0:4001:f00::/64` liegt.

Die relevanten gefundenen Nachbarn sind:

| IPv6-Adresse | MAC-Adresse | Status |
|---|---|---|
| `fe80::5054:ff:feb0:6296` | `52:54:00:b0:62:96` | STALE |
| `2001:4ca0:4001:f00::ff` | `52:54:00:b0:62:96` | STALE |
| `2001:4ca0:4001:f00::1` | `fe:54:00:3a:56:32` | STALE |
| `fe80::c62:7eff:fe66:9930` | `fe:54:00:3a:56:32` | STALE |
| `fe80::5054:ff:fe3a:5632` | `52:54:00:3a:56:32` | STALE |

Der Status `STALE` bedeutet nicht, dass der Host nicht existiert. Es bedeutet nur, dass der Eintrag gerade nicht frisch aktiv geprüft wurde. Der Host wurde vorher gelernt und ist in der Neighbor-Tabelle vorhanden.

---

## 6. Welche Rechner wurden dadurch gefunden?

Durch den Multicast-Ping und die Neighbor-Tabelle wurden folgende antwortende IPv6-Knoten im lokalen Segment sichtbar:

### Eigener Router gwsec

```text
Globale Adresse:     2001:4ca0:4001:f00::21
Link-Local-Adresse:  fe80::5054:ff:fe84:904
```

Diese Adresse antwortete direkt im Ping:

```text
64 bytes from fe80::5054:ff:fe84:904%ens8
```

### Weiterer Host / Router

```text
Globale Adresse:     2001:4ca0:4001:f00::ff
Link-Local-Adresse:  fe80::5054:ff:feb0:6296
MAC-Adresse:         52:54:00:b0:62:96
```

### secserver

```text
Globale Adresse:     2001:4ca0:4001:f00::1
Link-Local-Adresse:  fe80::c62:7eff:fe66:9930
MAC-Adresse:         fe:54:00:3a:56:32
```

Diese globale Adresse passt auch zu Aufgabe 6d, wo `2001:4ca0:4001:f00::1` als `secserver` gescannt wurde.

### Weiterer Host im lokalen Segment

```text
Link-Local-Adresse:  fe80::5054:ff:fe3a:5632
MAC-Adresse:         52:54:00:3a:56:32
```

Für diesen Host wurde in der Neighbor-Tabelle keine globale IPv6-Adresse aus `2001:4ca0:4001:f00::/64` angezeigt, aber er hat auf den Multicast-Ping geantwortet.

# Endgültige Antwort für Aufgabe 6e

```text
Das Brute-Force-Scannen des IPv6-Netzes 2001:4ca0:4001:f00::/64 ist nicht praktikabel, weil ein /64-Netz 2^64 mögliche Host-Adressen enthält. Das sind 18.446.744.073.709.551.616 Adressen. Ein vollständiger Scan würde dadurch extrem lange dauern.

Als Alternative wurde vom Router gwsec aus IPv6-Multicast verwendet. Das passende Interface ist ens8, weil es die Adresse 2001:4ca0:4001:f00::21/64 besitzt. Mit ping6 -c 3 -I ens8 ff02::1 wurde ein ICMPv6 Echo Request an alle IPv6-Knoten im lokalen Segment gesendet. Darauf antworteten mehrere Hosts. Anschließend wurden die bekannten Nachbarn mit ip -6 neigh show dev ens8 angezeigt.

Gefunden wurden unter anderem die antwortenden Link-Local-Adressen fe80::5054:ff:fe84:904, fe80::c62:7eff:fe66:9930, fe80::5054:ff:feb0:6296 und fe80::5054:ff:fe3a:5632. In der Neighbor-Tabelle waren außerdem die globalen Adressen 2001:4ca0:4001:f00::1 und 2001:4ca0:4001:f00::ff sichtbar. Die Adresse 2001:4ca0:4001:f00::1 entspricht dem secserver.
```
