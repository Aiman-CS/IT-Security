# Aufgabe 7c – Rootkit entfernen und Änderungen rückgängig machen

## Herangehensweise

Nachdem ein Rootkit entdeckt wurde (Aufgabe 7a), muss man systematisch **alle Änderungen** rückgängig machen. Die Reihenfolge ist wichtig:

1. **Rootkit-Datei entfernen/reparieren** – Zuerst die Quelle des Problems beseitigen, damit das Rootkit nicht erneut läuft
2. **Backdoor schließen** – Alle vom Rootkit angelegten Benutzer/Zugänge entfernen
3. **Gesammelte Daten löschen** – Vom Rootkit gesammelte sensible Informationen (Passwort-Hashes, Prozesslisten) entfernen
4. **Berechtigungen reparieren** – Alle vom Rootkit geänderten Dateiberechtigungen auf Normalzustand setzen
5. **Manipulierte Dateien bereinigen** – Fake-Einträge in History und anderen Dateien entfernen
6. **Verifikation** – Prüfen, ob alles sauber ist

**Wichtig:** Man muss wissen, was das Rootkit verändert hat (aus 7a), um gezielt alles rückgängig zu machen. In unserem Fall hat das Rootkit auf **pcsec2** folgendes gemacht:
- `/etc/cron.daily/passwd` modifiziert (Persistenz)
- Benutzer `a5stR0b0y` in `/etc/shadow` eingetragen (Backdoor)
- `/tmp/vexed` erstellt und Daten gesammelt (Exfiltration)
- Berechtigungen von `/var/log/*` auf 744 gesetzt (Verschleierung)
- Berechtigungen von `/root/.bash_history` auf 744 gesetzt
- Fake-Einträge in `/root/.bash_history` geschrieben (Verschleierung)

---

## Schritt 1: Rootkit-Skript durch saubere Version ersetzen

### Was ist das Problem?

Die Datei `/etc/cron.daily/passwd` auf pcsec2 wurde mit bösartigem Code erweitert. Sie wird täglich von Cron ausgeführt und würde das Rootkit jeden Tag erneut aktivieren. Deshalb muss sie **zuerst** repariert werden.

### Befehl:

```bash
printf '#!/bin/sh\ncd /var/backups || exit 0\nfor FILE in passwd group shadow gshadow; do\n        test -f /etc/$FILE              || continue\n        cmp -s $FILE.bak /etc/$FILE     && continue\n        cp -p /etc/$FILE $FILE.bak && chmod 600 $FILE.bak\ndone\n' > /etc/cron.daily/passwd
```

### Erklärung:

- `printf '...\n...\n'` = Gibt Text mit Zeilenumbrüchen (`\n`) aus
- `> /etc/cron.daily/passwd` = Überschreibt die Datei komplett mit dem neuen Inhalt
- Der Inhalt ist das **originale, saubere Skript** (identisch mit dem auf gwsec/pcsec1)

**Warum `printf` und nicht ein Heredoc (`cat << EOF`)?**
In einer SSH-Session kann ein Heredoc Probleme machen, weil das Terminal Zeilenumbrüche manchmal als einzelne Zeile interpretiert. `printf` mit `\n` ist zuverlässiger.

### Verifikation:

```bash
cat /etc/cron.daily/passwd
```

**Ausgabe:**
```
#!/bin/sh
cd /var/backups || exit 0
for FILE in passwd group shadow gshadow; do
        test -f /etc/$FILE              || continue
        cmp -s $FILE.bak /etc/$FILE     && continue
        cp -p /etc/$FILE $FILE.bak && chmod 600 $FILE.bak
done
```

```bash
wc -l /etc/cron.daily/passwd
```

**Ausgabe:**
```
7 /etc/cron.daily/passwd
```

7 Zeilen = korrekt (das kompromittierte hatte ~30+ Zeilen).

### Berechtigungen setzen:

```bash
chmod 755 /etc/cron.daily/passwd
```

- `755` = rwxr-xr-x = Owner kann lesen/schreiben/ausführen, alle anderen nur lesen/ausführen
- Cron-Skripte müssen ausführbar sein (`x`-Bit), sonst werden sie nicht ausgeführt

## Schritt 2: Backdoor-Benutzer aus `/etc/shadow` entfernen

### Was ist das Problem?

Das Rootkit hat bei jedem Lauf zwei Zeilen an `/etc/shadow` angehängt:
```
a5stR0b0y:shWm5UR68F3U8:0:0::/:/bin/bash
a5stR0b0y:x:0:0::/:/bin/bash
```

Obwohl das Format falsch ist (das ist passwd-Format, nicht shadow-Format), stellt es trotzdem ein Sicherheitsrisiko dar. Die Einträge müssen entfernt werden.

### Befehl:

```bash
sed -i '/a5stR0b0y/d' /etc/shadow
```

### Erklärung:

- `sed` = Stream Editor, bearbeitet Text zeilenweise
- `-i` = In-Place-Bearbeitung (ändert die Datei direkt, ohne Ausgabe auf stdout)
- `'/a5stR0b0y/d'` = Lösche (`d`) jede Zeile, die den String `a5stR0b0y` enthält
- `/etc/shadow` = Die zu bearbeitende Datei

### Verifikation:

```bash
grep "a5stR0b0y" /etc/shadow
```

**Ausgabe:**
```
(keine Ausgabe = kein Treffer = erfolgreich entfernt)
```

```bash
cat /etc/shadow
```

**Ausgabe:**
```
root:$6$cu2RKqEY$mu7CrscYpVo4UVgn5G7isJ/sHmx4O3Q1syr45ovzNMuNxLNpbDk/zeJa98Q85xTrwUzaUte8522kIh0BanzbP0:20563:0:99999:7:::
daemon:*:17598:0:99999:7:::
bin:*:17598:0:99999:7:::
...
secpgast:$6$KqdRLb2y$2vUkDVE1lg1ifoPVj8GlWa2jfQyywZY26heZnImebMyH/QC5gxE7C7isDYrAOhN6JUbxCvvNEKGs62n0tL33b/:20563:0:99999:7:::
```

Nur noch legitime Benutzer vorhanden.

### Berechtigungen der Shadow-Datei korrigieren:

```bash
chmod 640 /etc/shadow
```

- `640` = rw-r----- = Nur root kann lesen/schreiben, Gruppe `shadow` kann lesen
- Das ist die Standard-Berechtigung für `/etc/shadow` auf Debian

## Schritt 3: Gesammelte Daten löschen

### Was ist das Problem?

Das Rootkit hat in `/tmp/vexed` sensible Daten gesammelt:
- Prozessliste (`ps aux`)
- Alle Benutzernamen (`/etc/passwd`)
- Alle Passwort-Hashes (`/etc/shadow`)

Diese Datei muss gelöscht werden, damit die gesammelten Informationen nicht weiter zugänglich sind.

### Befehl:

```bash
rm /tmp/vexed
```

### Erklärung:

- `rm` = Remove, löscht eine Datei
- `/tmp/vexed` = Die vom Rootkit erstellte Sammeldatei

### Verifikation:

```bash
ls /tmp/vexed 2>&1
```

**Ausgabe:**
```
ls: cannot access '/tmp/vexed': No such file or directory
```

Datei erfolgreich gelöscht.

## Schritt 4: Log-Berechtigungen reparieren

### Was ist das Problem?

Das Rootkit hat `chmod 744 /var/log/*` ausgeführt. Das bedeutet:
- Vorher: `640` (rw-r-----) = Nur root und Gruppe `adm` können Logs lesen
- Nachher: `744` (rwxr--r--) = Jeder kann Logs lesen + das Execute-Bit ist gesetzt (unsinnig für Logdateien)

Außerdem wurden Log-Verzeichnisse ebenfalls auf falsche Berechtigungen gesetzt.

### Befehle:

```bash
find /var/log -type f -exec chmod 640 {} \;
```

### Erklärung:

- `find /var/log` = Durchsucht das Verzeichnis `/var/log`
- `-type f` = Nur reguläre Dateien (keine Verzeichnisse)
- `-exec chmod 640 {} \;` = Führt `chmod 640` auf jede gefundene Datei aus
- `{}` = Platzhalter für den Dateinamen
- `\;` = Ende des `-exec`-Befehls

```bash
find /var/log -type d -exec chmod 755 {} \;
```

### Erklärung:

- `-type d` = Nur Verzeichnisse
- `chmod 755` = rwxr-xr-x = Verzeichnisse brauchen das `x`-Bit damit man sie betreten kann

### Verifikation:

```bash
ls -la /var/log/ | head -10
```

**Ausgabe (vorher – kompromittiert):**
```
-rwxr--r--  1 root        adm  11049 May  4 12:19 auth.log
-rwxr--r--  1 root        adm  37834 May  3 06:25 auth.log.1
drwxr--r--  2 root        root  4096 May  4 10:26 apt
```

**Ausgabe (nachher – repariert):**
```
-rw-r-----  1 root        adm  11049 May  4 12:19 auth.log
-rw-r-----  1 root        adm  37834 May  3 06:25 auth.log.1
drwxr-xr-x  2 root        root  4096 May  4 10:26 apt
```

**Worauf achten:**
- Logdateien sollten NIEMALS das `x`-Bit haben (es sind Textdateien, keine Programme)
- `640` = rw-r----- ist der Standard für Logs
- `744` = rwxr--r-- ist FALSCH und ein Hinweis auf Manipulation

## Schritt 5: Bash-History reparieren

### Was ist das Problem?

Das Rootkit hat zwei Dinge mit der Bash-History gemacht:
1. Berechtigungen auf `744` gesetzt (statt `600`)
2. Fake-Befehle hineingeschrieben, um den echten Verlauf zu verschleiern

Die Fake-Befehle sind:
- `ls -a`
- `uptime`
- `du . -m`
- `w`
- `dig something.org`
- `man time`
- `man hostname`

Diese wiederholen sich dutzendfach in der History.

### Berechtigungen korrigieren:

```bash
chmod 600 /root/.bash_history
```

### Erklärung:

- `600` = rw------- = Nur root kann die History lesen/schreiben
- Normalerweise ist die History nur für den Besitzer lesbar

### Fake-Einträge entfernen:

```bash
sed -i '/^ls -a$/d;/^uptime$/d;/^du \. -m$/d;/^w$/d;/^dig something.org$/d;/^man time$/d;/^man hostname$/d' /root/.bash_history
```

### Erklärung:

- `sed -i` = In-Place-Bearbeitung
- `/^ls -a$/d` = Lösche Zeilen die EXAKT "ls -a" enthalten (^ = Zeilenanfang, $ = Zeilenende)
- `;` = Trennt mehrere sed-Befehle
- `/^w$/d` = Lösche Zeilen die exakt nur "w" sind
- `/^dig something.org$/d` = Lösche die Fake-dig-Einträge
- `/^man time$/d` = Lösche die Fake-man-Einträge
- `\. ` = Das `.` muss escaped werden, da es in Regex "beliebiges Zeichen" bedeutet

### Verifikation:

```bash
ls -la /root/.bash_history
```

**Ausgabe:**
```
-rw------- 1 root root 1820 May  4 12:50 /root/.bash_history
```

- `600` (rw-------) = korrekte Berechtigung
- Dateigröße deutlich kleiner als vorher (die ~500 Fake-Zeilen sind weg)
